## 三、详细学习路线

### Phase 1：LLM 基础与 API 调用（第 1-2 个月）

#### 3.1 理解 LLM 的能力边界

```
LLM 能做什么：
✅ 文本生成、总结、翻译、改写
✅ 代码生成、解释、调试
✅ 结构化数据提取
✅ 多轮对话、角色扮演
✅ 推理与分析

LLM 不能做什么（或做不好）：
❌ 精确计算（数学计算不可靠）
❌ 实时信息（训练数据有截止日期）
❌ 长期记忆（上下文窗口有限）
❌ 执行操作（需要 Tool Calling 桥接）
❌ 事实性保证（会"幻觉"）
```

#### 3.2 主流 LLM API 对比

| 模型 | 提供商 | 特点 | 适用场景 |
|------|--------|------|----------|
| Claude 4 系列 | Anthropic | 长上下文、代码强、安全 | 复杂推理、代码、长文档 |
| GPT-4o | OpenAI | 生态最成熟、多模态 | 通用场景、Function Calling |
| Gemini 2.5 | Google | 超长上下文、多模态 | 长文档分析 |
| DeepSeek V3 | DeepSeek | 性价比高、代码强 | 成本敏感场景 |
| Qwen 3 | 阿里 | 中文能力强、开源 | 国内业务、私有化部署 |

#### 3.3 API 调用实践

**第一步：学会调用 API**

```typescript
// 使用 Vercel AI SDK（推荐，统一接口）
import { generateText, streamText } from 'ai'
import { anthropic } from '@ai-sdk/anthropic'

// 非流式调用
const result = await generateText({
  model: anthropic('claude-sonnet-4-6'),
  prompt: '解释什么是 RAG',
})
console.log(result.text)

// 流式调用
const stream = streamText({
  model: anthropic('claude-sonnet-4-6'),
  prompt: '写一个 Vue3 组件',
})
for await (const chunk of stream.textStream) {
  process.stdout.write(chunk)
}
```

**第二步：理解 Token 与成本**

```
概念：
- Token：LLM 计费的最小单位（约 1 个汉字 = 1-2 tokens）
- 上下文窗口：单次对话的最大 Token 数
- 输入/输出价格：输入通常比输出便宜

成本控制策略：
1. 使用合适的模型（简单任务用 Haiku，复杂任务用 Sonnet/Opus）
2. 控制上下文长度（只传必要信息）
3. 缓存常见请求
4. 流式输出提升用户感知速度
```

#### 3.4 流式输出在前端的实现

```typescript
// 前端：SSE / Fetch Stream
async function chat(message: string) {
  const response = await fetch('/api/chat', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ message }),
  })

  const reader = response.body!.getReader()
  const decoder = new TextDecoder()

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    const chunk = decoder.decode(value)
    // 实时更新 UI
    appendToChat(chunk)
  }
}
```

### Phase 2：RAG（检索增强生成）（第 3-4 个月）

#### 3.1 为什么需要 RAG

```
LLM 的核心问题：
1. 知识截止：训练数据有时效性
2. 私有数据：不知道你的企业内部知识
3. 幻觉：可能生成看似正确但错误的信息

RAG 的解法：
用户提问 → 检索相关知识 → 将知识作为上下文 → LLM 基于上下文回答

效果：让 LLM 基于你的真实数据回答，大幅降低幻觉
```

#### 3.2 RAG 架构

```
完整 RAG 流程：

文档处理：
  文档 → 分块(Chunking) → Embedding → 向量数据库

查询流程：
  用户问题 → Embedding → 向量检索 → Top-K 相关文档
  → 拼接 Prompt（问题 + 检索结果）→ LLM 生成回答
```

#### 3.3 关键技术点

| 技术点 | 说明 | 推荐方案 |
|--------|------|----------|
| 文档分块 | 按语义切分文档 | 递归字符分割 / 语义分割 |
| Embedding | 文本转向量 | OpenAI Embedding / BGE-M3 |
| 向量数据库 | 存储和检索向量 | Chroma（本地）/ Pinecone（云）/ Milvus（生产） |
| 检索策略 | 提高召回率 | 混合检索（向量 + 关键词） |
| 重排序 | 提高相关性 | Cohere Rerank / BGE-Reranker |

#### 3.4 代码实现

```typescript
// 使用 LangChain.js 实现 RAG
import { Chroma } from '@langchain/community/vectorstores/chroma'
import { OpenAIEmbeddings } from '@langchain/openai'
import { RecursiveCharacterTextSplitter } from 'langchain/text_splitter'
import { RetrievalQAChain } from 'langchain/chains'

// 1. 文档分块
const splitter = new RecursiveCharacterTextSplitter({
  chunkSize: 1000,
  chunkOverlap: 200,
})
const docs = await splitter.splitDocuments(rawDocuments)

// 2. 向量化存储
const vectorStore = await Chroma.fromDocuments(docs, new OpenAIEmbeddings(), {
  collectionName: 'my-knowledge-base',
})

// 3. 检索 + 生成
const chain = RetrievalQAChain.fromLLM(model, vectorStore.asRetriever(4))
const answer = await chain.call({ query: '用户的问题' })
```

### Phase 3：Function Calling 与 AI Agent（第 5-7 个月）

#### 3.1 Function Calling 原理

```
核心概念：
LLM 本身不能"做事"，但可以"决定做什么"

Function Calling 流程：
1. 你告诉 LLM 有哪些工具可用（工具定义）
2. LLM 判断需要调用哪个工具（返回工具调用请求）
3. 你执行工具调用，把结果返回给 LLM
4. LLM 基于工具结果生成最终回答

示例：
用户：北京今天天气怎么样？
LLM：我需要调用 get_weather 工具 → { tool: "get_weather", args: { city: "北京" } }
你：执行 API 调用，结果 { temp: 32, condition: "晴" }
LLM：北京今天天气晴，气温 32°C，比较炎热，注意防晒。
```

#### 3.2 代码实现

```typescript
// 使用 Vercel AI SDK 的 Tool Calling
import { generateText, tool } from 'ai'
import { z } from 'zod'

const result = await generateText({
  model: anthropic('claude-sonnet-4-6'),
  tools: {
    weather: tool({
      description: '获取指定城市的天气信息',
      parameters: z.object({
        city: z.string().describe('城市名称'),
      }),
      execute: async ({ city }) => {
        const data = await fetchWeather(city)
        return data
      },
    }),
    calculator: tool({
      description: '执行数学计算',
      parameters: z.object({
        expression: z.string().describe('数学表达式'),
      }),
      execute: async ({ expression }) => {
        return eval(expression) // 实际使用时需要安全处理
      },
    }),
  },
  prompt: '北京今天天气怎么样？如果温度超过30度，告诉我体感温度。',
  maxSteps: 5, // 允许多步工具调用
})
```

#### 3.3 AI Agent 架构

```
Agent = LLM + Tools + 记忆 + 规划

Agent 类型：
┌─────────────────────────────────────────┐
│ ReAct Agent                              │
│ 思考 → 行动 → 观察 → 思考 → ... → 回答  │
│ 最常用的 Agent 模式                       │
├─────────────────────────────────────────┤
│ Plan-and-Execute Agent                   │
│ 规划完整步骤 → 逐步执行 → 调整计划        │
│ 适合复杂多步任务                          │
├─────────────────────────────────────────┤
│ Multi-Agent                              │
│ 多个 Agent 协作，各有专长                  │
│ 适合大型复杂任务                          │
└─────────────────────────────────────────┘
```

### Phase 4：AI 应用架构与工程化（第 8-12 个月）

#### 4.1 AI 应用的架构模式

```
模式 1：API 直连（最简单）
前端 → LLM API
适用：简单对话、单轮任务

模式 2：RAG 增强
前端 → 后端 API → 向量检索 + LLM
适用：知识库问答、企业内部应用

模式 3：Agent 架构
前端 → 后端 API → Agent（LLM + Tools + Memory）
适用：复杂任务、多步操作

模式 4：Multi-Agent
前端 → 后端 API → Agent Orchestrator → 多个专业 Agent
适用：企业级复杂场景
```

#### 4.2 AI 应用的用户体验设计

```
关键 UX 原则：

1. 即时反馈
   - 流式输出，不要让用户等
   - 加载状态、进度提示

2. 透明性
   - 展示 AI 的推理过程
   - 工具调用可视化
   - 信息来源标注

3. 可控性
   - 用户可以中断、修改、重试
   - 人工审核节点
   - 不确定性提示

4. 渐进式展示
   - 先展示核心结果
   - 详细信息可展开
   - 相关推荐

5. 错误处理
   - 优雅降级
   - 重试机制
   - 人工兜底
```

#### 4.3 评估与优化

| 评估维度 | 指标 | 方法 |
|----------|------|------|
| 回答质量 | 准确率、相关性 | 人工评估 + LLM-as-Judge |
| 延迟 | 首 Token 时间、总时间 | 监控埋点 |
| 成本 | 每次调用 Token 消耗 | API 日志分析 |
| 用户满意度 | 点赞率、修正率 | 用户反馈 |

### 项目 4 重点：AI 增强的表单生成器

这是结合你 PMS 经验的最佳项目：

```
核心功能：
- 用户用自然语言描述表单需求

- 基于 Schema 渲染表单（对接你熟悉的组件库）
- AI 辅助填写、校验、提交
- 表单模板库 + AI 推荐

技术栈：
- 前端：Vue3 + Element Plus / PMS 组件库
- 后端：Next.js API Routes
- AI：Vercel AI SDK + Function Calling
- 存储：Chroma（模板检索）

亮点：
- 结合了你已有的企业级后台经验
- 解决了真实痛点（表单开发效率低）
- 可直接在现有项目中落地
```
