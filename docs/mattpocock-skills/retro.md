# `retro`

> **分类**：engineering（工程类）｜**调用方式**：用户手动调用

- **一句话定位**：回顾一次编码会话，建议改的是 agent 的**环境**，而不是代码。
- **调用方式**：用户手动调用
- **适用场景**：一次构建之后（尤其是跑偏的那次）想收尾复盘时；在 `ask-matt` 主流程中它是 `/code-review` 之后的最后一步；在 `/diagnosing-bugs` 修完 bug 后追问"什么能预防这类 bug"时，也在同一会话里跑它。
- **核心指令**：
  1. **先加载写作风格**：调用 Skill 工具的 `writing-for-agents` 获取写作风格指南（v1.3.1 起总是加载）。
  2. **读取一手材料**：读取用户指定的那次会话的一手资料，可能需要在本机搜索会话日志；用户没指定就默认当前这一次。要在清理上下文之前、在它所回顾的那个会话里跑它；清理之后就改为指向那次会话的日志。
  3. **按类别寻找改进候选**：**导航**（agent 找对文件有多容易？文件间有没有隐藏依赖？加一条**导航指针**会不会更好？会话花很久才找到某条信息时用它）；**自动化检查**（有没有能抓住 agent 所犯错误的检查？lint、类型检查、测试、文件系统 linter；**先读仓库自己的检查命令**（`package.json`/构建工具的 `lint`/`check` 脚本、CI workflow），因为"已经存在但没接线或静默失效的检查"本身就是发现，而不是让你另造一个）；**编码规范**（该给 reviewer agent 加一条新规则吗？已有规则该删还是该澄清？reviewer 漏掉了某个错误时用它）；**全局 AGENTS.md**（有哪些 steering 指令该下沉到编码规范或自动化检查？文件特别大时用它，仓库范围或用户全局范围都算）；**工具经济性**（agent 有没有做了可以精简的昂贵工具调用？哪个 CLI/MCP 特别费 token？agent 做了昂贵调用时用它）；**空操作**（steering 文件里哪些指令并不改变 agent 的行为？文件又大又难用时用它）；**信息可达性**（有没有机会扩大 agent 的信息获取？比如 tee dev server 日志、给第三方服务只读权限；关键信息对 agent 不可得时用它）。
  4. **先分类，再开方**：每条编码规范发现都要先分类。**机械性违规**（固定的语法模式、被禁用的 API、import 形态、文件位置规则）必须得到一个**确定性检查**，没有例外：仓库自己 linter 里的自定义规则、新的 pre-commit hook、或新的 CI job，取仓库语言和现有护栏下最便宜的那种；默认是"造检查"而不是"写规则"。`CODING_STANDARDS.md` 只留给真正的**判断调用**（跨文件一致性、"与周围风格一致"、任何护栏都无法替代的东西）。**一个完全没有护栏的仓库本身就是一条发现**：没有 pre-commit hook、也没有跑 lint/typecheck/test 的 CI job，意味着未经 lint 的仓库是长期被浪费的机会，不是中性默认。
  5. **呈现**：按严重程度排序，把这些候选交给用户。
- **分工依据**：所有工作都经过实施与评审两个阶段。实施 agent 的**上下文压力**最大（探索、写代码、调试失败都归它），评审 agent 压力最小（只拿到一个 diff，无需探索，常常不用写代码或调试）。所以编码规范该由评审 agent 来执行，而不是实施 agent。
- **文件职责**：`CLAUDE.md`/`AGENTS.md` 会进任何在本仓库工作的 agent 的上下文窗口，要极其节省，通常只放**导航指针**；`CODING_STANDARDS.md` 在评审时读而非实施时读，超过 1000 行就加指向 docs 目录的导航指针；docs 作为被其他文件指向的参考文件，先找现有的再写新的；skills 用于承载文档（它的 description 会进 agent 的上下文窗口）或用户主动调用的命令，遵循 `writing-for-agents` 的建议。
