# `domain-modeling`

> **分类**：engineering（工程类）｜**调用方式**：模型自动调用

- **一句话定位**：主动构建和打磨项目的领域模型，统一术语、消除歧义、将关键决策记录为 ADR。
- **调用方式**：模型自动调用
- **适用场景**：讨论代码库术语时；直接编写或编辑 `GLOSSARY.md` 时；记录或编辑 ADR 时。（仅仅为了查词汇而**读** `GLOSSARY.md` 不算，那是任何技能都能做的一行习惯；本技能用于**改变**模型，而不只是消费它。）
- **核心指令**：
  - **文件结构**：单上下文仓库用根目录 `GLOSSARY.md` + `docs/adr/`；仓库根存在 `GLOSSARY-MAP.md` 则表示多上下文，地图指向每个上下文自己的 `GLOSSARY.md`（各上下文可有自己的 `docs/adr/`）。文件按需懒创建：第一个术语解决时才建 `GLOSSARY.md`，第一篇 ADR 需要时才建 `docs/adr/`。
  - **会话中的主动纪律**：
    - **对着术语表挑战**：用户用词与 `GLOSSARY.md` 既有语言冲突时立即指出（"你的术语表把 cancellation 定义为 X，你指的似乎是 Y，是哪个？"）。
    - **锐化模糊语言**：对含混或重载的术语提出精确的规范名称（"你说 'account'，指的是 Customer 还是 User？"）。
    - **讨论具体场景**：发明探测边界、迫使概念边界清晰化的场景来压测领域关系。
    - **与代码交叉验证**：用户描述的工作方式与代码不符时立即提出。
    - **就地更新 `GLOSSARY.md`**：术语解决后当场更新，不批量处理；`GLOSSARY.md` 必须完全不含实现细节，它不是 spec、不是草稿本、不是实现决策的存放处。
    - **审慎创建 ADR**：仅当"难以逆转"、"缺乏上下文会令人惊讶"、"真实权衡的结果"三条同时满足时才提议，缺一条就跳过。
