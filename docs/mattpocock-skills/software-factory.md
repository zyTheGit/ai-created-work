# `software-factory`

> **分类**：in-progress（开发中草稿，实验性新技能）｜**调用方式**：用户手动调用

- **一句话定位**：为"软件工厂"的设计提供共享词汇：工厂要执行的任务，以及它接入的各项服务。
- **调用方式**：用户手动调用
- **适用场景**：想设计一套由 agent 把工单、PR 和日程转化为已合并代码、并运行在用户选择的远程基础设施上的系统（软件工厂）时；通常与 `/grilling` 会话配合使用，用它统一术语、补齐设计决策。
- **核心指令**：
  1. **先统一词汇，且只用这些词**：**Task**（工厂执行的一类工作，定义一次、运行多次：review、explore、implement、ratchet；避免 job / workflow / action）、**Trigger**（启动一次 run 的事件：工单或 git host 的变更、编排器的时钟、或另一次 run）、**Run**（一次任务在一次 runner 上的完整执行，视为黑盒，永不等待人类；避免 session）、**Runner**（一次性执行机器，跑完不留痕迹，唯一记忆是工单系统、git host 和编排器；避免 server / host / box / sandbox）、**Ticket tracker**（工单所在地，也是工厂的人类界面：人建工单调度工作、在评论里与 agent 对话）、**Ticket source**（工厂外部创建工单的东西：反馈按钮、监控、错误追踪、收件箱）、**Git host**、**Orchestrator**（接收 trigger、在 runner 上启动 run、记录排队/在飞/完成状态）、**Observability platform**（run 的日志、追踪与状态，可选：runner 或编排器产品往往已展示足够信息）。用户用了 _Avoid_ 里的词，就当场纠正为规范术语。
  2. **从用户的问题出发，而不是从工厂出发**：未分诊的工单、等待自动评审的 PR、要迁移到的更严格自动检查、没人读的 bug。用户说不出要建什么时，先读 `EXAMPLE-TASKS.md`，按问题挑选任务。
  3. **起步要慢（三道刹车）**：每个 trigger 都是油门，只有油门没有刹车就会变成"slop cannon"。三道刹车是**自动检查**（类型、lint、测试等确定性门禁，每次 run 必须通过）、**自动评审**（独立 run 冷读 diff，对照编码规范和工单）、**人工评审**（合并前由人读 PR，它抓到的问题要沉淀为新的自动检查或更锋利的自动评审）。一次只加一个自动 trigger 并先限流（十份 bug 报告取一份、时钟每天一次），每个 PR 都保留人工评审；信任建立后再放开油门，每个 run 循环最多重试几次就交回人类。
  4. **填满每个槽位**：服务即槽位，一个产品可占多个槽位，一台服务器可托管多个服务。技能给出三种并排参考设计（全部 GitHub / Linear 工单 / 自有 tracker），每个槽位列出候选产品。选型时先读对应调查文档（`TICKET-TRACKERS.md`、`GIT-HOSTS.md`、`RUNNERS.md`、`OBSERVABILITY-PLATFORMS.md`）建立方向感，再自行调研当前选项。原则是**买服务、建任务**：任务承载用户的设计，服务是通用的；优先使用现成的工单系统。
  5. **逐项拷问每个任务**：①什么触发它？②它做什么、读写哪些服务？③它接下来触发什么？④人在哪里重新介入？⑤什么阻止两个 run 做同一件事？每个 ticket source 还要回答：什么阻止它重复建同一张工单？
  6. **完成标准**：每个槽位都指定了产品（可观测平台允许明确选"无"），每个任务和 ticket source 都回答了全部问题，设计才算完成。
- **配套参考文件**：`EXAMPLE-TASKS.md`（按问题分组的示例任务，含 trigger 与后续触发链）、`TICKET-TRACKERS.md` / `GIT-HOSTS.md` / `RUNNERS.md` / `OBSERVABILITY-PLATFORMS.md`（每个槽位的产品类型调查与选型问题）。
