## 一、engineering（工程类，20 个）

### `ask-matt`

- **一句话定位**：技能路由器，帮你选择当前情境最适合的 skill 或工作流。
- **调用方式**：用户手动调用
- **适用场景**：面对一个任务不知道该用哪个 skill 时；想了解所有可用工作流及其关系时；需要规划从想法到交付的完整路径时。
- **核心指令**：
  - **前置纪律**：断言某个技能做什么、或建议跳过它的某一步之前，先读那个技能的 SKILL.md；这里的摘要只用于定向。
  - **主流程（idea → ship）**：`/grill-with-docs`（在**工作目录**里才用它：有状态，把所学沉淀进 `GLOSSARY.md` 和 ADR；不在工作目录用 `/grill-me`，两者跑同一个 `/grilling` 原语，但只有前者留痕）→ 需要可运行答案的问题经 `/handoff` 进出 `/prototype` → 多会话构建走 `/to-spec` + `/to-tickets`（每个工单声明阻塞边），然后逐工单 `/implement`（之间 `/clear`）或整体 `/implement-spec`；单会话构建直接 `/implement`。无论哪条路，代码都由 `/tdd` 一个红绿切片驱动、`/code-review` 收尾；PR 由 `/pr` 塑造正文；`/retro` 收口，它改的是 agent 的**环境**而非代码。
  - **入口匝道**：`/triage`（只处理**别人**创建的 issue，`/to-tickets` 产出的工单已 agent-ready，别再 triage）、`/diagnosing-bugs`（修复落地后在同一会话跑 `/retro` 问"什么本可以预防这个 bug"；若结论是缺一条好接缝，才去 `/improve-codebase-architecture`）、`/wayfinder`（庞大模糊工程，两个易错见下）。
  - **代码库健康**（`/improve-codebase-architecture` 找深化机会）与**底层词汇层**（`/domain-modeling` 管领域语言，`/codebase-design` 管深模块词汇），后两者是模型自动调用的参考技能。
  - **阶段边界决策树**：phase 是会话内的一块工作（grilling、实现、QA），两个 phase 之间按序问五个问题：① 能继续吗（下一 phase 需要本 phase 当一手来源，或 smart zone 还装得下）→ **Continue**；② 上下文对后续无关吗 → **`/clear`**（棋盘上最便宜的一步，且可恢复）；③ 需要**搬运**上下文吗（换 harness、换目录、交给同事、phase 中途 fork 支线）→ **`/handoff`**，它买的是**可移植性**，没有东西在旅行就不需要它；④ 任务能 AFK 吗 → **subagent**；⑤ 否则 **`/compact`**。`/compact` 是**默认而非首选**，坐在树的最底部，因为上面四问都更便宜或更精确；只有 Continue 保留一手来源，其余四步都把它换成有损摘要。
  - **wayfinder 的两个易错**：**过度伸手**（它比单次 grill 更慢更密，只留给真正装不进一个会话的想法，范围清楚的功能该去 `/grill-with-docs`）；**在交接处迷路**（地图清了就交接、不自己建：并回主流程的 `/to-spec`，而不是把地图直接接进 `/implement`，只有确实变小的努力才直通 `/implement`）。另补上了此前缺失的 `/grilling` 路由：`grill-me` 与 `grill-with-docs` 按"你是否在一个工作目录里"分流。
  - **上下文卫生**：步骤 1-3 保持同一个未压缩的上下文窗口（`/to-tickets` 之后才 compact 或 clear）；smart zone 约 **150k tokens**，接近时别硬撑着降级运行，在最近的 phase 边界 `/compact` 后继续。`/retro` 要在它回顾的那个会话里跑。

### `code-review`

- **一句话定位**：双轴并行的代码审查，同时检查代码是否符合本仓库文档化的编码规范（Standards）和是否忠实实现了原始 issue / spec（Spec）。
- **调用方式**：模型自动调用
- **适用场景**：用户想审查一个分支、PR 或工作变更时；需要"review since X"时；`/implement` 完成后自动触发。
- **核心指令**：
  1. **锚定基准点**：确认用户指定的 commit/branch/tag，用 `git diff <fixed-point>...HEAD`（三点 diff，对比 merge-base）获取变更，并记下 `git log <fixed-point>..HEAD --oneline` 的提交列表；基准点无法解析或 diff 为空时**在此处失败**，不要带进两个并行 sub-agent。
  2. **定位 Spec 来源**：按优先级搜索，commit message 中的 issue 引用（`#123`、`Closes #45`、GitLab `!67`）> 用户作为参数传入的路径 > `docs/`、`specs/`、`.scratch/` 下与分支或功能匹配的 spec 文件 > 询问用户。若用户说没有 spec，Spec 子 agent 将跳过并报告 "no spec available"。
  3. **定位 Standards 来源**：**搜索仓库**中每一个记录"代码该如何写"的文件，`CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在时必须在列。此外 Standards 轴始终携带一套固定的 Fowler 代码异味基线（_Refactoring_ 第 3 章，12 种），两条约束：仓库文档标准永远覆盖基线；每条异味都是带标签的启发式判断（如 "possible Feature Envy"），绝不是硬性违规；工具已强制的一律跳过。
  4. **并行派发两个 sub-agent**：以 harness 中立的方式把两次调用**一起发出、放到前台**，再汇总它们返回的报告。Standards agent 需拿到 diff 命令、提交列表、第 3 步找到的规范文件清单，**以及完整粘贴进来的异味基线**（它没有别的途径获取），外加"区分硬性违规与判断性异味、跳过工具已强制的、400 字以内"的指令；Spec agent 需拿到 spec 内容，报告缺失或部分实现的需求、范围蔓延、以及实现看起来不对的地方，每条发现引用 spec 原文。spec 缺失则跳过 Spec agent 并在最终报告中注明。
  5. **汇总**：分 `## Standards` 和 `## Spec` 两节原样呈现两个报告，**不合并不重排**（两轴是故意分开的：符合全部规范却实现了错的东西 = Standards 过 Spec 挂；照 issue 做了却破坏项目约定 = 反之），末尾给出每轴发现总数与该轴内最严重的问题，不跨轴选冠军。
  6. **前置条件**：issue tracker 本应已提供；若没有，**告知用户去运行 `/setup-matt-pocock-skills`**，不要试图用 Skill tool 调它（用户手动类技能）。

### `codebase-design`

- **一句话定位**：深度模块设计的共享词汇体系，为模块的接口、接缝、深度提供统一的精确语言。
- **调用方式**：模型自动调用
- **适用场景**：设计或改进模块接口时；寻找深化机会时；需要让代码更可测试或更易被 AI 导航时；其他 skill 需要深度模块词汇时。
- **核心指令**：
  - **核心术语**（严格使用，不得漂移成 component / service / API / boundary）：**Module**（有接口和实现的任意规模实体，从函数到跨层切片）、**Interface**（调用者正确使用模块所需知道的一切：类型签名、不变量、顺序约束、错误模式、必需配置、性能特征）、**Implementation**（模块内部代码）、**Adapter**（在接缝处满足接口的具体物，描述角色而非内容）、**Depth**（接口的行为杠杆率）、**Seam**（Michael Feathers：接口所在的位置，能不在此处编辑就改变行为的地方）、**Leverage**（调用者得到的回报）、**Locality**（维护者得到的局部性）。
  - **深度 vs 浅度**：深模块 = 小接口 + 大实现；浅模块 = 大接口 + 薄实现（应避免）。设计时追问：能否减少方法数？能否简化参数？能否隐藏更多复杂度？
  - **核心原则**：深度是接口的属性而非实现的属性（模块内部可以有仅供自己测试用的**内部接缝**）；删除测试（删掉模块后复杂度是集中了，还是只是搬家）；接口即测试面（想测到接口之外，说明模块形状不对）；一个 adapter 意味假设性接缝，两个才是真实接缝，没有东西真的在变就别造接缝。
  - **可测试性设计**：接受依赖而非创建依赖；返回结果而非产生副作用；小接口面积。
  - **设计两遍（Design It Twice，源自 Ousterhout，原 `design-an-interface` 技能已并入此处）**：为已选定的深化候选项探索替代接口时，先写出面向用户的问题空间说明（新接口必须满足的约束、依赖分类、一段仅用于把约束讲实的示意代码），展示给用户后立即并行 spawn **3 个以上** sub-agent，每个以**不同的设计约束**产出一套**截然不同**的接口（Agent 1 最小化接口只留 1-3 个入口点、Agent 2 最大化灵活性、Agent 3 为最常见调用方优化、必要时 Agent 4 用 ports & adapters 处理跨接缝依赖）；每个 agent 输出接口、调用示例、接缝后藏了什么、依赖策略与 adapter、以及取舍。sub-agent 派发保持 harness 中立。逐个展示后按**深度**、**局部性**、**接缝位置**三维对比，并给出有主见的推荐，可以提议混合方案。
  - **被拒绝的框定**：深度不是"实现行数 / 接口行数"之比（那会奖励给实现注水）；interface 不等于 TS `interface` 关键字或类的公开方法；不用 boundary（与 DDD 的 bounded context 冲突）。
  - **深入**：给定依赖关系去深化一个模块簇见 `DEEPENING.md`（依赖分类、接缝纪律、replace-don't-layer 测试）。

### `diagnosing-bugs`

- **一句话定位**：针对疑难 bug 和性能回退的系统化诊断循环，从构建反馈回路到修复并清理。
- **调用方式**：模型自动调用
- **适用场景**：用户说"diagnose" / "debug"时；报告某功能损坏 / 报错 / 失败 / 变慢时；遇到间歇性 bug 或两个已知良好状态之间的回归时。
- **核心指令**：
  - **Redact（脱敏）**：脱敏是**每项展示动作的第一个动作**。凡要展示命令、输出或抓取产物，先把密钥写成 `<REDACTED>`；构造循环时针对**环境变量**取值，让凭证留在环境里，而不是出现在你展示的内容中；抓取产物（HAR、日志转储、core dump）自带 auth header，只引用携带信号的那些行。脱敏后的输出不足以诊断时，明说并向用户索要脱敏后的产物。
  - **Phase 1：构建反馈回路**（核心技能，其余都是机械的）：按优先级尝试 10 种方式（失败测试 > curl 脚本 > CLI 对比 > 无头浏览器 > 重放 trace > 一次性 harness > 属性 / fuzz > 二分 > 差分 > 人机协作脚本）。循环必须做到紧凑（秒级）、确定性、agent 可运行。非确定性 bug 的目标是**提高复现率**而非完美复现。完成标准是：能说出**一条命令**，且已经**至少跑过一次**并展示其（脱敏后的）调用与输出，它红得了、确定性、够快、可无人值守运行；人只在 `scripts/hitl-loop.template.sh` 里进场（注意其中的 `capture` 会把值回打到终端，所以登录时获取观测值仍应作为 `step`）。在这样一条命令存在之前就埋头读代码建理论，正是本技能要防的失败。
  - **Phase 2：复现 + 最小化**：确认复现的是**用户**描述的失败模式（而非附近的其他失败），每轮只裁掉一个元素并重跑循环，直到每个剩余元素都不可删。
  - **Phase 3：假设**：测试任何假设之前先生成 3-5 个排名假设，每个必须可证伪（"如果 X 是原因，那么改变 Y 将让 bug 消失"），测试前先给用户看。
  - **Phase 4：探测**：每个探针都要对应 Phase 3 的某条预测，每次只改一个变量；优先用 debugger / REPL，所有 debug log 加唯一前缀（如 `[DEBUG-a4f2]`）以便一次 grep 清干净。性能问题先建基线测量再二分。
  - **Phase 5：修复 + 回归测试**：先写回归测试再修复，但必须有**正确的接缝**（测试要在调用点复现真实 bug 模式；接缝太浅只会给出虚假信心），无正确接缝时**这本身就是发现**。靠变异代码或夹具强造红灯时，先 `diff` 一份原始副本**证明变异确实落地**，再相信红灯。
  - **Phase 6：Cleanup**：纯清理清单，原 repro 不再复现、回归测试通过（或记录"无接缝"）、所有 `[DEBUG-...]` 已删、临时原型已删或移到明确标记的调试位置、正确的假设写进 commit / PR message。**不再**包含向 `/improve-codebase-architecture` 的事后交接（那来自一个自主、常无人值守的流程，没有人类能接住失败的调用）；这一步改由主流程在修复落地后跑 `/retro` 完成。
  - **前置习惯**：探索代码库时读 `GLOSSARY.md`（若存在）以建立清晰心智模型，并查看所涉区域的 ADR。

### `domain-modeling`

- **一句话定位**：主动构建和打磨项目的领域模型，统一术语、消除歧义、将关键决策记录为 ADR。
- **调用方式**：模型自动调用
- **适用场景**：讨论代码库术语时；直接编写或编辑 `GLOSSARY.md` 时；记录或编辑 ADR 时。（仅仅为了查词汇而**读** `GLOSSARY.md` 不算，那是任何技能都能做的一行习惯；本技能用于**改变**模型，而不只是消费它。）
- **核心指令**：
  - **文件结构**：单上下文仓库用根目录 `GLOSSARY.md` + `docs/adr/`；仓库根存在 `GLOSSARY-MAP.md` 则表示多上下文，地图指向每个上下文自己的 `GLOSSARY.md`（各上下文可有自己的 `docs/adr/`）。文件按需懒创建：第一个术语解决时才建 `GLOSSARY.md`，第一篇 ADR 需要时才建 `docs/adr/`。
  - **会话中的主动纪律**：
    - **对着术语表挑战**：用户用词与 `GLOSSARY.md` 既有语言冲突时立即指出（"你的术语表把 cancellation 定义为 X，你指的似乎是 Y，是哪个？"）。
    - **锐化模糊语言**：对含混或重载的术语提出精确的规范名称（"你说 'account'，指的是 Customer 还是 User？"）。
    - **讨论具体场景**：发明探测边界、迫使概念边界清晰化的场景来压测领域关系。
    - **与代码交叉验证**：用户描述的工作方式与代码不符时立即提出。
    - **就地更新 `GLOSSARY.md`**：术语解决后当场更新，不批量处理；`GLOSSARY.md` 必须完全不含实现细节，它不是 spec、不是草稿本、不是实现决策的存放处。
    - **审慎创建 ADR**：仅当"难以逆转"、"缺乏上下文会令人惊讶"、"真实权衡的结果"三条同时满足时才提议，缺一条就跳过。

### `grill-with-docs`

- **一句话定位**：带文档持久化的深度访谈，在打磨计划或设计的同时，把 ADR 和术语表一路写出来。
- **调用方式**：用户手动调用
- **适用场景**：在**工作目录**里需要打磨想法 / 计划 / 设计时；希望在访谈过程中同步生成 `GLOSSARY.md` 和 ADR 文档时；作为主流程（idea → ship）的起点。
- **核心指令**：
  - 显式调用 Skill 工具两次：一次 `"grilling"`（访谈原语），一次 `"domain-modeling"`（领域建模）。
  - **按轮次运行前沿**：每轮一次提出一组问题，与 `/grilling` 的纪律一致；事实由 agent 补齐，决策归用户。
  - 与 `/grill-me` 的分流：`grill-with-docs` 是**有状态**的，把学到的内容持久化进 `GLOSSARY.md` 和 ADR，留下文档痕迹；`/grill-me` 无状态、不落盘。两者跑同一个 `/grilling` 原语，只要仓库在，`grill-with-docs` 就是严格更好的那个。

### `implement`

- **一句话定位**：基于 spec 或工单实现功能，驱动 TDD 红绿循环并在完成后自动 code review。
- **调用方式**：用户手动调用
- **适用场景**：有明确的 spec 或 ticket 需要实现时；主流程中 `/to-tickets` 拆分后的逐个实现阶段（每个工单配一个全新上下文窗口）；单会话构建中直接在当前上下文实现。
- **核心指令**：
  - 按用户描述的 spec 或工单实现工作。**若用户传入了工单引用，先从 issue tracker 拉取它并陈述其标题**再开工；引用有歧义时先问清。
  - 尽可能调用 Skill 工具的 `"tdd"`，在预先约定的接缝处一个红绿切片一个红绿切片地推进。
  - 定期运行类型检查、定期运行单个测试文件，最后运行一次完整测试套件。
  - 完成后调用 Skill 工具的 `"code-review"` 对工作进行双轴审查（Standards + Spec）。
  - 把工作提交到当前分支。

### `implement-spec`

- **一句话定位**：一次跑完整个 spec 的实施：把工单当作任务图，在就绪的前沿上并行推进，全部落到一条集成分支。
- **调用方式**：用户手动调用
- **适用场景**：`/to-spec` + `/to-tickets` 的产物已在手，希望一次性把整份 spec 建完，而不是逐个工单 `/implement`；在 `ask-matt` 主流程中，它是逐工单 `/implement`（每个之间 `/clear` 上下文）的**并行替代路线**，适合"想编排这次构建而不想自己开每一张工单"的时候。
- **核心指令**：
  1. **任务图与前沿**：工单不是步骤清单，而是带阻塞关系的**任务图**，因此总有一批就绪的**前沿**工单可被抓取。目标是整个 spec 落在**一条集成分支**上，每个工单都按 issue tracker 关闭工作的方式解决。
  2. **稀疏通信 + 上下文指针**：与 subagent 的往来保持稀疏，主要靠**上下文指针**传递（spec、工单、研究笔记、此前的 commit）；指针已能提供的信息不要重复传递。
  3. **步骤**：读 spec 和工单以理解任务图；（可选）先用 **exploration subagent** 做工单所需的探索，并把 markdown 笔记存到仓库之外、所有未来 subagent 都能访问的目录，让 implementer 专心实现而非探索；创建集成分支；用 **implementer subagent** 实施每张工单，各自在自己的 worktree 和自己的分支上，尽可能后台并行以求最大并发。
  4. **每个 implementer**：开工前确认自己的 worktree 基于集成分支（不是就重置过去）；调用 Skill 工具的 `tdd` 来构建该工单；报告完成前把集成分支的尖端合并进自己的分支，使每次合并都是快进。
  5. **合并推进**：implementer 完成后，用 **merger subagent** 把它的工作合并到集成分支；若这改变了可认领工单的**前沿**，就再拉起更多 implementer 去抢新工单，以维持最大并发。
  6. **收尾**：所有工单完成后，在集成分支上调用 Skill 工具的 `code-review`，审查提出的全部问题交给**单个** implementer subagent 一次修完；若存在 draft PR 则标记为 ready for review，否则按 tracker 的方式逐个解决工单并汇报集成分支；最后清理所有 implementer worktree。
  7. **关于 PR**：目标是集成分支而不是 PR。只有当 issue tracker 通过 PR 关闭工作、或用户明确要求时才开 PR，且必须在第一次合并之后（没有领先 main 的提交的分支开不了 PR），并标记它关闭该 spec 与工单；没有 PR 时，工单按 tracker 关闭工作的方式解决。
  8. **前置条件**：issue tracker 应已提供；没提供就**告知用户运行 `/setup-matt-pocock-skills`**（该技能由人类手动执行），而不是默默默认使用 `gh`。

### `improve-codebase-architecture`

- **一句话定位**：扫描代码库寻找深化机会，生成可视化 HTML 报告，然后对用户选择的候选方案进行深度访谈。
- **调用方式**：用户手动调用
- **适用场景**：有空闲时间想改善代码库架构时；想发现浅模块并深化它们时；想提高代码的可测试性和 AI 可导航性时。
- **核心指令**：
  1. **探索（先做 YAGNI 范围过滤）**：深化一个模块的回报在于让**未来**对它的改动更容易，所以要给"最近改过的部分"额外加权。用户指定了方向（模块、子系统、痛点）就用用户的；否则回读约 **20 条** commit message 找出持续出现的**热点路径**，让它们把注意力先拉过去（没人碰的代码里的深化机会是永远兑现不了的重构）；改动过于分散、找不到明显热点时再扩大范围。先读 `GLOSSARY.md` 和该区域的 ADR，再派 sub-agent（harness 中立）有机探索，关注浅模块、理解成本高、纯函数抽取过度导致真实 bug 藏在调用方式里（无 locality）、跨接缝泄漏、难以通过现有接口测试的区域；对可疑浅模块执行删除测试（删掉它是让复杂度集中了，还是只是搬家）。
  2. **呈现 HTML 报告**：写入 OS 临时目录的自包含 HTML 文件（按 `$TMPDIR` → `/tmp` / `%TEMP%` 解析，文件名 `architecture-review-<timestamp>.html`），打开并告知绝对路径。布局用 CDN 版 Tailwind，图用 CDN 版 Mermaid（关系是图状的才用，编辑式可视化交给手写 div/SVG）。每个候选方案渲染一张卡片：涉及文件、问题、方案、以 locality 和 leverage 表述的收益、手绘前后对比图、推荐强度徽章（Strong / Worth exploring / Speculative），末尾给**首选推荐**。用 `GLOSSARY.md` 的领域词汇加 `/codebase-design` 的建筑词汇（不得漂移成 component / service / API / boundary）。与已有 ADR 冲突的候选，只有在摩擦真实到值得重开 ADR 时才列出，并在卡片上明确标注。报告写完**先不提议接口**，只问"你想深入哪一个"。
  3. **访谈循环**：用户选定后调用 Skill 工具的 `"grilling"` 走决策树（约束、依赖、深化后模块的形状、接缝后放什么、哪些测试存活），同时调用 `"domain-modeling"` 保持领域模型最新（新术语写入 `GLOSSARY.md`、模糊术语当场打磨、用户以站得住的理由否掉候选时提议 ADR）；想探索替代接口就再调 `"codebase-design"` 的设计两遍并行 sub-agent 模式。

### `pr`

- **一句话定位**：PR 正文应有的形状：用最小可视化讲清改动，用前后证据证明它生效，再给出合并危险性判断。
- **调用方式**：模型自动调用
- **适用场景**：需要撰写 PR 正文时；在 `ask-matt` 主流程中，工作以 pull request 形式提交时由 agent 自动触发的收尾路线（agent 每次写 PR 都会伸手去拿它）。
- **核心指令**：跳过所有开场白，正文保持简短，并使用 `GLOSSARY.md` 中的项目领域术语。模板分三部分：
  1. **Summary（摘要）**：挑一个能讲清关键点的**最小可视化**。按需选用一种或几种，但几乎用不上全部：逻辑或算法用**伪代码**；运行时控制流用**调用树**；UI 结构用**组件树**（含关键的 state 与模块边界）；文件职责或大范围重构用**浅层文件树**；组件交互、控制流或数据流用 **Mermaid**；当重点就是"改了什么"且周围形态已存在时用 **diff**（按主题匹配 diff 形态：组件变更、文件布局变更、调用树变更、状态/控制流变更）；大部分是新增、省略上下文会掩盖归属或顺序、或用户需要一份可复制的目标形态时，直接贴整段代码。每张可视化要紧挨它支撑的那句短文本，只保留回答当前问题或解决当前争论点所需的调用、文件、props、state 和边界，不要把人淹掉。
  2. **Evidence（证据）**：证明改动生效的具体证据，前后对比。截图是 S 级（环境就绪且变更是视觉性的）；基于执行的证据是 A 级（测试结果、控制台输出），用伪代码展示那个测试从失败到通过。
  3. **Merge Danger（合并危险性）**：说明这是**单向门**还是**双向门**（双向门可以走回去，单向门不行；便宜地可回滚意味着低风险，涉及破坏性动作或难以逆转的决策的是单向门）。再给出**爆炸半径**（此次改动潜在的影响或范围，要考虑各种可能：布局位移、对消费方的破坏、移动端适配等），用一句话概括，并可附上合并后的潜在连带影响。
- **署名**：Summary 的可视化做法改编自 Dex Horthy（Humanlayer）的 `show-me` 技能，在该技能的 `CREDITS.md` 中署名，frontmatter 的 `metadata.credits` 记录了 skill、作者、组织和来源 URL。

### `prototype`

- **一句话定位**：一次性原型代码，用可运行的代码回答一个具体的设计问题（状态模型是否合理 / UI 应该长什么样）；原型本身是一手资料。
- **调用方式**：模型自动调用
- **适用场景**：需要验证状态模型 / 业务逻辑是否合理时；需要探索 UI 应该长什么样时；设计问题难以在纸面上定论时；主流程中需要从 grilling 分支出来用代码回答具体问题时。
- **核心指令**：
  - **选择分支**（选错会浪费整个原型）："这个逻辑 / 状态模型感觉对吗？"→ **逻辑分支**，产出一个**单个可分享的自包含 HTML 文件**（纯 HTML / CSS / JS，无框架、无打包器、无服务器，非开发者双击即可打开），把状态机推过纸上难以推理的用例；"这该长什么样？"→ **UI 分支**，在同一条路由上生成若干个截然不同的 UI 变体，用 URL search 参数加浮动底栏切换。问题 genuinely 含糊且用户不在线时，按周围代码默认（后端模块 → 逻辑，页面 / 组件 → UI），并在原型顶部声明该假设。
  - **逻辑分支的 HTML 结构**（自上而下）：① 标题加一行说明，写清要探索的问题；② **当前状态面板**，带标签的字段而非裸 JSON 转储，每次点击后重渲染，顺带指出刚刚变了什么；③ **自由操作按钮**，每个动作一个，始终可用，任意顺序乱点；④ 一组分标签页的**引导式演练**，每个标签是一个场景（一段白话说明它设定什么、该看什么），下方列出该场景要按的按钮顺序，每一步都是真按钮，开始演练时重置到已知初始状态。场景要覆盖开心路径、棘手边界，以及一次**本该非法的尝试**。用非开发者能懂的语言写，不用代码的语言。
  - **可移植的纯逻辑模块**：把真正回答问题的那段逻辑放进单个 `<script>` 块，写成可提升进真实代码库的小而纯的模块（reducer / 状态机 / 纯函数集 / 方法面清晰的类），**不碰 DOM**（页面调用它，没有反向流动）。页面是抛弃层，这个模块不是：原型答完问题后，验证过的 reducer / 机器 / 函数集自行升入真实模块，HTML 外壳才进抛弃分支。
  - **通用规则**：从第一天起就是一次性的并在命名上标明，放在实际使用位置旁边（UI 原型沿用项目既有路由约定，别另造顶层结构）；一条命令即可运行（UI 用项目 task runner，逻辑 demo 是双击打开的 HTML）；默认无持久化，状态在内存中，问题明确涉及数据库时才碰临时库或带 "PROTOTYPE, wipe me" 名字的本地文件；跳过打磨（无测试、无多余错误处理、无抽象）；每次操作后展示完整相关状态。
  - **"可丢弃"不等于"删掉"**：原型作为**可运行的证据**留在从 main 切出的 throwaway 分支 `prototype/<name>` 上（自包含单文件，在那里依然随时可重跑），并在实现 issue 上留一条指向该分支的上下文指针。**答案**（结论 + 它解决了哪个问题）落在 issue、ADR 或 commit 里；主分支只保留已验证的决策。

### `research`

- **一句话定位**：针对高可信一手资料进行调研，并将结果以 Markdown 文件形式保存到仓库中。
- **调用方式**：模型自动调用
- **适用场景**：用户需要调研某个主题、收集文档或 API 事实、将阅读性工作委托给后台 agent 时触发；`/wayfinder` 的 research 工单也由它并行烧掉。
- **核心指令**：启动一个**后台 agent** 执行调研，主 agent 继续工作。后台 agent 的职责：(1) 针对**一手资料**（官方文档、源码、规范、第一方 API）进行调查，而非它们的二手转述，每条结论都要回溯到拥有它的那个源头；(2) 将调研结果写成一份 Markdown 文件，每条结论都附上引用来源；(3) 保存到仓库中已有的笔记目录，遵循现有约定，若无约定则放在合理位置并说明存放路径。

### `retro`

- **一句话定位**：回顾一次编码会话，建议改的是 agent 的**环境**，而不是代码。
- **调用方式**：用户手动调用
- **适用场景**：一次构建之后（尤其是跑偏的那次）想收尾复盘时；在 `ask-matt` 主流程中它是 `/code-review` 之后的最后一步；在 `/diagnosing-bugs` 修完 bug 后追问"什么能预防这类 bug"时，也在同一会话里跑它。
- **核心指令**：
  1. **先加载写作风格**：调用 Skill 工具的 `writing-for-agents` 获取写作风格指南（v1.3.1 起总是加载）。
  2. **读取一手材料**：读取用户指定的那次会话的一手资料，可能需要在本机搜索会话日志；用户没指定就默认当前这一次。要在清理上下文之前、在它所回顾的那个会话里跑它；清理之后就改为指向那次会话的日志。
  3. **按类别寻找改进候选**：**导航**（agent 找对文件有多容易？文件间有没有隐藏依赖？加一条**导航指针**会不会更好？会话花很久才找到某条信息时用它）；**自动化检查**（有没有能抓住 agent 所犯错误的检查？lint、类型检查、测试、文件系统 linter；**先读仓库自己的检查命令**（`package.json`/构建工具的 `lint`/`check` 脚本、CI workflow），因为"已经存在但没接线或静默失效的检查"本身就是发现，而不是让你另造一个）；**编码规范**（该给 reviewer agent 加一条新规则吗？已有规则该删还是该澄清？reviewer 漏掉了某个错误时用它）；**全局 AGENTS.md**（有哪些 steering 指令该下沉到编码规范或自动化检查？文件特别大时用它，仓库范围或用户全局范围都算）；**工具经济性**（agent 有没有做了可以精简的昂贵工具调用？哪个 CLI/MCP 特别费 token？agent 做了昂贵调用时用它）；**空操作**（steering 文件里哪些指令并不改变 agent 的行为？文件又大又难用时用它）；**信息可达性**（有没有机会扩大 agent 的信息获取？比如 tee dev server 日志、给第三方服务只读权限；关键信息对 agent 不可得时用它）。
  4. **先分类，再开方**：每条编码规范发现都要先分类。**机械性违规**（固定的语法模式、被禁用的 API、import 形态、文件位置规则）必须得到一个**确定性检查**，没有例外：仓库自己 linter 里的自定义规则、新的 pre-commit hook、或新的 CI job，取仓库语言和现有护栏下最便宜的那种；默认是"造检查"而不是"写规则"。`CODING_STANDARDS.md` 只留给真正的**判断调用**（跨文件一致性、"与周围风格一致"、任何护栏都无法替代的东西）。**一个完全没有护栏的仓库本身就是一条发现**：没有 pre-commit hook、也没有跑 lint/typecheck/test 的 CI job，意味着未经 lint 的仓库是长期被浪费的机会，不是中性默认。
  5. **呈现**：按严重程度排序，把这些候选交给用户。
- **分工依据**：所有工作都经过实施与评审两个阶段。实施 agent 的**上下文压力**最大（探索、写代码、调试失败都归它），评审 agent 压力最小（只拿到一个 diff，无需探索，常常不用写代码或调试）。所以编码规范该由评审 agent 来执行，而不是实施 agent。
- **文件职责**：`CLAUDE.md`/`AGENTS.md` 会进任何在本仓库工作的 agent 的上下文窗口，要极其节省，通常只放**导航指针**；`CODING_STANDARDS.md` 在评审时读而非实施时读，超过 1000 行就加指向 docs 目录的导航指针；docs 作为被其他文件指向的参考文件，先找现有的再写新的；skills 用于承载文档（它的 description 会进 agent 的上下文窗口）或用户主动调用的命令，遵循 `writing-for-agents` 的建议。

### `setup-matt-pocock-skills`

- **一句话定位**：为仓库配置工程技能所需的基础设施：issue tracker、triage 标签体系和领域文档布局。
- **调用方式**：用户手动调用
- **适用场景**：首次使用其他工程技能前运行一次，完成仓库级配置。
- **核心指令**：这是一个**提示驱动**的技能（非确定性脚本），流程为"探索 → 展示 → 确认 → 写入"。
  - **步骤 1 探索**：读 `git remote -v` 与 `.git/config`、根目录 `CLAUDE.md` / `AGENTS.md`（是否已有 `## Agent skills` 段）、`GLOSSARY.md` 与 `GLOSSARY-MAP.md`、`docs/adr/` 与 `src/*/docs/adr/`、`docs/agents/`、`.scratch/`；判断 **triage 技能是否已安装**（这决定 Section B 跑不跑）；识别 **monorepo 信号**（`pnpm-workspace.yaml`、`package.json` 的 `workspaces`、有自己 `src/` 的 `packages/*`），这些只出现在真正的大型多包仓库，没有就是单上下文，而单上下文是几乎所有仓库的情况。
  - **步骤 2 逐项确认**（每节以推荐答案开头，一个词即可接受）：
    - **Section A：issue tracker**。默认姿态是这些技能为 GitHub 设计：remote 指向 GitHub 就提议 GitHub，指向 GitLab（`gitlab.com` 或自托管）就提议 GitLab，否则提供 GitHub / GitLab / 本地 markdown（`.scratch/<feature>/`） / 其他（Jira、Linear，用一段自由文本记录）。选择写进 `docs/agents/issue-tracker.md`。GitHub 与 GitLab 模板带一个"PRs as a request surface"开关，**默认关**：保持关闭且不要主动提起，想要外部 PR 进 triage 队列的用户事后自己翻。
    - **Section B：triage 标签**。triage 技能没安装就**整节跳过**（没装的技能不需要标签）。装了也只问**一个**问题："要保留默认 triage labels 吗？（推荐：是）"。默认是五个规范角色，标签字符串与角色同名：`needs-triage`、`needs-info`、`ready-for-agent`、`ready-for-human`、`wontfix`。选是就原样写下；选否（通常是 tracker 已用别的名字）才收集覆盖映射。**Section B 在 GitHub 或 GitLab 上跑过之后，会创建 tracker 缺失的每个标签**（`gh label create` / `glab label create`）。
    - **Section C：领域文档**。默认**单上下文**（根目录一个 `GLOSSARY.md` + `docs/adr/`），这适合几乎所有仓库，**直接写、不询问**；只有探索发现了 monorepo 信号才提供多上下文（根 `GLOSSARY-MAP.md` 指向各上下文的 `GLOSSARY.md`）并让用户确认。
  - **步骤 3-4：确认并写入**。展示 `## Agent skills` 块草稿和 `docs/agents/` 下各文件内容，让用户先改再写。写入时：`CLAUDE.md` 存在就编辑它，否则 `AGENTS.md` 存在就编辑它，两者都没有才问用户建哪个；已有的 `## Agent skills` 块**就地更新**而非追加重复。`### Triage labels` 子块和 `docs/agents/triage-labels.md` 只在 triage 已安装且 Section B 跑过时才写。本地 markdown tracker 的约定是：spec 叫 `.scratch/<feature-slug>/spec.md`（不是 `PRD.md`），实现工单**一文件一工单** `.scratch/<feature-slug>/issues/<NN>-<slug>.md`（从 `01` 编号，绝不是一个合并的 `tickets.md`）。
  - **步骤 5**：告知用户设置完成、哪些工程技能现在会读这些文件，并说明 `docs/agents/*.md` 事后可直接编辑，只有换 tracker 或推倒重来才需要重跑本技能。

### `tdd`

- **一句话定位**：测试驱动开发参考指南，确保 red-green-refactor 循环产出值得保留的测试。
- **调用方式**：模型自动调用
- **适用场景**：用户希望以测试先行方式开发功能或修复 bug、提到"red-green-refactor"、或需要集成测试时触发。
- **核心指令**：**好测试的标准**：测试通过公共接口验证行为而非实现细节，代码可以整个换掉而测试不该挂；测试应像规格说明（"user can checkout with valid cart"），能经受住重构。**Seam（接缝）**：测试只能放在**预先约定**的公共边界上，写任何测试之前先把待测接缝写下来并与用户确认，没有确认过接缝就不写测试；问一句"公共接口是什么，我们该测哪些接缝？"，并给每个提议的接缝附一行说明，讲清**它能挡住什么、会漏掉什么**。接口本身的形状有疑问时（模块该多深、接缝该放哪）调用 Skill 工具的 `"codebase-design"` 取词汇，那是参考不是会话。**三大反模式**：(1) 实现耦合（mock 内部协作者、测私有方法、走侧信道验证）；(2) 同义反复（断言用与代码相同的方式重算期望值，期望值必须来自独立的真相来源）；(3) 水平切片（先写所有测试再写所有实现，那验证的是**想象中**的行为），应改为**垂直切片**，一个测试 → 一个实现 → 循环，每个测试都是一颗回应上一轮教训的**曳光弹**。**循环规则**：先写失败测试（red），再写最少代码使其通过（green），不预先实现未来测试、不加投机功能；每个周期只处理一个接缝、一个测试、一个最小实现；**重构不属于循环**，归入 `code-review` 阶段。**前置习惯**：探索代码库时读 `GLOSSARY.md`（若存在），让测试名与接口词汇对上项目的领域语言，并尊重所涉区域的 ADR。

### `to-spec`

- **一句话定位**：将当前对话上下文综合为一份规格文档（spec），并发布到项目 issue tracker；"spec"是唯一术语，不再称 PRD。
- **调用方式**：用户手动调用
- **适用场景**：用户希望把已讨论的内容整理成正式规格文档时使用，无需额外访谈。
- **核心指令**：**不采访用户**，直接综合已有对话和代码库理解生成 spec。issue tracker 与 triage 标签词汇本应已提供；若没有，**告知用户去运行 `/setup-matt-pocock-skills`**，不要试图用 Skill tool 调它。流程：(1) 探索仓库了解代码现状，全文使用项目领域术语表的词汇，遵循所涉区域的 ADR；(2) 勾画将要测试该功能的接缝，优先现有接缝、尽量取高层，新接缝越少越好（理想数量为 1），并与用户确认这些接缝符合预期；(3) 按模板编写 spec 并发布到 issue tracker，打上 `ready-for-agent` triage 标签，不需要额外 triage。**Spec 模板包含**：Problem Statement（用户视角的问题）、Solution（用户视角的方案）、User Stories（极长的编号列表，格式 `As an <actor>, I want a <feature>, so that <benefit>`）、Implementation Decisions（要建 / 改的模块及其接口、技术澄清、架构决策、schema 变更、API 契约；**不含**具体文件路径或代码片段，除非原型产出的某个片段比散文更精确地编码了决策，如状态机、reducer、schema、类型形状，则内联并注明来自原型，只留决策丰富的部分）、Testing Decisions（什么是好测试、测哪些模块、测试的先例）、Out of Scope、Further Notes。

### `to-tickets`

- **一句话定位**：将计划、spec 或对话拆分为一组 tracer-bullet 式垂直切片工单，每个工单声明阻塞依赖关系，发布到配置的 tracker。
- **调用方式**：用户手动调用
- **适用场景**：用户希望把 spec 或讨论结果拆分成可执行的工单时使用。
- **核心指令**：issue tracker 与 triage 标签词汇本应已提供；若没有，**告知用户去运行 `/setup-matt-pocock-skills`**，不要试图用 Skill tool 调它。流程：(1) **收集上下文**，从对话上下文出发；用户传了引用（spec 路径、issue 编号或 URL）就拉取并读完正文与评论。(2) **探索代码库**（可选），用项目领域术语表的词汇写工单标题和描述，尊重所涉区域 ADR，并寻找 prefactor 机会（"先让改动变容易，再做容易的改动"）。(3) **拆分垂直切片**：每个切片是一条窄但**完整**的端到端路径（贯穿 schema、API、UI、测试各层），不是某一层的水平切片；完成即可独立演示或验证；大小适合放进一个全新的上下文窗口；prefactor 排在最前。为每个工单写明**阻塞边**（必须先完成的其他工单），没有阻塞者的可以立刻开工。**宽幅重构是垂直切片的例外**：一个机械改动（改列名、改共享符号类型）的影响面扇向整个代码库，单次编辑就打断成千上万个调用点，没有垂直切片能落绿，此时按 **expand–contract** 排序，先 expand 在旧形式旁加新形式，再按影响面分批（每包 / 每目录）迁移、每批一个工单且被 expand 阻塞、逐批保持 CI 绿，最后 contract 删旧形式、该工单被所有迁移批阻塞；连分批都无法独自保持绿时，保留顺序但让它们共用一条集成分支，共同阻塞一个"集成并验证"工单，绿只在那里承诺。(4) **向用户确认**：展示编号列表，每个工单给出标题、Blocked by、以及它交付的端到端行为，问粒度是否合适、阻塞边是否正确（每个工单只依赖真正卡住它的工单）、是否要合并或再拆，迭代到批准。(5) **发布工单**，发布方式取决于 tracker，工单本身一样，只有阻塞边的形态不同：本地 tracker 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下**一文件一工单**、从 `01` 按依赖序（阻塞者在前）编号，文件里 "Blocked by" 列出它依赖的编号 / 标题，**绝不是一个合并的 tickets 文件**；真实 tracker（GitHub、Linear 等）按依赖序一工单一 issue，让阻塞边能引用真实标识，平台有原生阻塞关系就用原生，否则把 "Blocked by" 设为阻塞 issue 集合，来源是既有 issue 时把每个工单挂成它的 **sub-issue**，打上 `ready-for-agent` 标签。**不关闭也不修改任何父 issue**。之后按**前沿**推进：任何阻塞者已全部完成的工单；纯线性链就是从上到下。

### `triage`

- **一句话定位**：将 issue 和外部 PR 在 triage 状态机中流转，分类、验证、追问、编写 agent 可执行的简报。
- **调用方式**：用户手动调用
- **适用场景**：维护者需要评估和处理 issue tracker 上的 issue 或外部 PR 时使用；只处理**别人**创建的、原始到来的东西。
- **核心指令**：**角色体系**：2 个分类角色（bug / enhancement）+ 5 个状态角色（needs-triage → needs-info / ready-for-agent / ready-for-human / wontfix），每个被 triage 的 issue 恰好带一个分类角色和一个状态角色；状态角色冲突时先标记并问维护者。状态转移：未标记的通常先进 needs-triage，再到 needs-info / ready-for-agent / ready-for-human / wontfix；needs-info 在报告者回复后回到 needs-triage；维护者可随时覆盖。**triage 期间发到 tracker 的每条评论和 issue 都必须以免责声明开头**：`> *This was generated by AI during triage.*`。**PR 是附了代码的 issue**（仓库配置把外部 PR 当请求面时才纳入），同样的角色、状态和机器；发现阶段只捞**外部** PR，并给每行标 `[PR]` 或 `[issue]`（这个过滤只用于发现，被点名指出的 PR 一律照 triage）。
  - **查看待处理项**：查询 tracker，按未标记、needs-triage、needs-info（自上次 triage 笔记以来报告者有新活动）三桶、由旧到新展示，给出计数和每项一行摘要，让维护者挑。
  - **处理具体 issue / PR**：(1) **收集上下文**，完整阅读（PR 还要读 diff），解析此前的 triage 笔记避免重问已解决的问题，用项目领域术语表探索代码库，并跑两项检查：**冗余**（按领域概念而非请求措辞搜索是否已有实现，有就是"已实现"的 wontfix）和**此前被拒**（读 `.out-of-scope/*.md`）；(2) **建议**，给出分类与状态推荐及理由加一段相关代码摘要，等指示；(3) **验证声明**，任何追问之前先确认它站得住：bug 就照报告者步骤复现，PR 就确认 diff 确实做了它声称的事（签出、跑相关测试或命令），报告"已确认（含代码路径）/ 失败 / 细节不足"；(4) **必要时追问**，调用 Skill 工具两次，`"grilling"` 与 `"domain-modeling"`，一轮问题一轮问题地理清，术语当场打磨、`GLOSSARY.md` / ADR 就地更新；(5) **执行结果**，ready-for-agent 发 agent brief，ready-for-human 用同样结构但注明为何不能委派，needs-info 发 triage notes，wontfix 关闭（已实现：指向它在哪，**不写** `.out-of-scope/`，那是给**被拒**请求的；被拒的 bug：礼貌解释后关闭；被拒的 enhancement：写进 `.out-of-scope/` 并从评论链接过去）。
  - **按轮次推进**：grilling 一轮一次一组问题，不要一次倒完。
  - **快速状态覆盖**：维护者说"move #42 to ready-for-agent"就照办，先确认要做的事（角色变更、评论、关闭）再动手，跳过 grilling；若没经过 grilling 就移到 ready-for-agent，问一句要不要写 agent brief。
  - **恢复上次会话**：读既有 triage 笔记，看报告者是否已回答未决问题，先给出更新后的全貌再继续，不重问已解决的问题。
  - **前置条件**：角色名是规范名，tracker 里实际标签字符串可能不同，映射本应已提供；若没有，**告知用户去运行 `/setup-matt-pocock-skills`**，不要试图用 Skill tool 调它。

### `wayfinder`

- **一句话定位**：把超大型工作项规划为 issue tracker 上的**决策工单**地图，逐个解决直到通往目标的路径清晰。
- **调用方式**：用户手动调用
- **适用场景**：面对一个超出单个 agent 会话容量的大型模糊目标（制定 spec、锁定决策、规划数据迁移等），从这里到**目的地**的路还看不清时使用。
- **核心指令**：
  - **规划，不做**：默认只规划。每张工单解决一个决策，地图在"路已清晰、动手前再无可决"时完成；想直接干活的冲动通常说明你已到地图边缘、该交接了。某个 effort 可在其 **Notes** 里覆盖这一点，把执行带进地图。
  - **按名字引用**：地图和每张工单都是 issue，都有标题。在人类阅读的一切内容（叙述、地图的 Decisions-so-far）里只叫它的**名字**，绝不用裸 id、编号或 slug；id 和 URL 不消失，但只包在名字里面。
  - **地图（Map）**：tracker 上带 `wayfinder:map` 标签的单个 issue，是唯一规范制品；它是**索引不是仓库**，只列出已做的决策并指向承载细节的工单，从不重述。正文含 Destination、Notes、Decisions so far（已关闭工单一节一条，gist + 链接）、Not yet specified（战争迷雾）、Out of scope。
  - **工单**：地图的子 issue，正文就是一个问题，大小对齐一个 100K token 的 agent 会话；带 `wayfinder:<type>` 标签（research / prototype / grilling / task），**绝不打 triage 标签**（它们是决策，不是实现工作）。会话的**第一个动作**是把它 assign 给自己来认领。阻塞用 tracker 的**原生**依赖关系（这样前沿能在 tracker 自己的 UI 里可视化）；没有原生阻塞的 tracker 才退回正文约定。当某张工单的所有阻塞者都已关闭，它即**未阻塞**；**前沿**就是开放、未阻塞、未认领的子工单。
  - **工单类型**：Research（AFK，调 Skill 工具的 `"research"` 由 subagent 解决）、Prototype（HITL，调 `"prototype"` 做个便宜粗糙可反应的实物）、Grilling（HITL，对话，默认类型，调 Skill 工具两次 `"grilling"` 与 `"domain-modeling"`）、Task（HITL 或 AFK，决策前必须先做的手工活，它**做**而不**决**，靠解锁决策挣得位置）。答案不写在正文里，落在解决时的记录中。
  - **战争迷雾**：地图刻意不完整。看得见还说不清的问题写进 Not yet specified；判定标准是**现在能否精确说出问题**（不是能否回答）。解决一张工单会清掉它前方的雾，把新变得可表述的东西**一次一张**毕业成工单。
  - **范围之外**：雾只朝目的地聚集，超出目的地的不是雾而是 out of scope，写进独立小节，永不毕业；已存在但被发现越过目的地的工单**直接关闭**并在该节留一行 gist + 原因 + 链接。
  - **两种调用模式**：**Chart**（用户带一个模糊想法来）命名目的地 → 再次 grill 但**广度优先**地铺前沿（若这一步没翻出任何雾，说明不需要地图，停下问用户想怎么走）→ 建地图 → 把现在能指定的工单建成子 issue，**第二遍**再接阻塞边和交叉引用（issue 需要先有 id，占位的 `#<n>` 会自动链到无关 issue）→ **为每张 research 工单并行派 subagent 调 `"research"`**，把发现落在 throwaway 的 `research/<name>` 分支上并留上下文指针，**推分支但不开 PR**，它永不合并，绘图也不因此停下 → 停下，绘图是一个会话的工作。**Work**（用户带一个地图 URL 或编号来）加载地图的低分辨率视图 → 选工单（用户没指定就取前沿第一张）并**先认领** → 按标签类型解决，按需 zoom → 记录结论：发**解决评论**、关闭 issue、往 Decisions-so-far 追加一条上下文指针 → 新增工单（先建后接）并毕业已可表述的雾。
  - **铁律与易错**：**一个会话最多解决一张工单**，research 工单是"一次会话一个工单"的唯一例外。**不要 triage labels、不要占位引用、不要开调研 PR**。地图清晰后交接给 `/to-spec`（把地图的关联决策塌成可建的计划）而非直接 `/implement`；把地图直接接进 `/implement` 会跳过这次塌缩、丢掉关联细节。工单是**决策工单**：它的解答是一个决策，而不是一片待建的实现切片（术语建立后 "ticket" 仍是日常用词）。issue tracker 本应已提供；若没有，**告知用户去运行 `/setup-matt-pocock-skills`**；确实没有 tracker 时默认用本地 markdown tracker。

### `wizard`

- **一句话定位**：生成一个交互式 bash 向导脚本，带人一步步走完只有人类能执行的手动流程。
- **调用方式**：模型自动调用（`/wizard` 手动调用同样有效；模型调用只会增加 agent 的触达范围）
- **适用场景**：第三方服务配置、一次性迁移、A→B 状态割接等需要打开每个 URL、说明点哪里、捕获值并写进 `.env` 文件和 GitHub Actions secrets 的繁琐手动操作；agent 碰到"只有人能做的步骤"时会自己拉起它，而不是在聊天里甩一串编号指令。
- **核心指令**：
  1. **它是什么**：一个 bash 脚本，逐 stage 带人走一段手工做起来繁琐、每次向 AI 重讲一遍也繁琐的流程：打开每个 URL、说清点哪里复制什么、捕获值、写进该在的地方（`.env`、GitHub secrets）、每个阶段都确认、并显示还剩几个阶段。默认是临时的：为一次运行而生，存到 scratch 或 `scripts/` 路径，活干完就删；只有用户想要一条该住在仓库里的可重复配置路径时才提交，并从 README 链接过去。
  2. **UX 已由模板解决，你的工作只是划范围和写阶段**：捆绑的 `template.sh` 已预解决了这些体验：按阶段计数的进度显示（v1.2.3 起去掉了 `TOTAL_MINUTES` 和剩余时间，进度只按阶段数）、确认闸门、跨平台打开 URL（含 WSL）、隐藏式密钥输入、幂等的 `.env` upsert、`gh secret`/`gh variable` 写入并在 `gh` 不可用时优雅降级、收尾的跳过摘要。`STAGES` 标记以上的库代码在每个向导里完全相同，这种一致性正是重点，**绝不手改**。每个 `stage` 会清屏，所以一个 stage 只做一件聚焦的事，别让人需要的内容滚出屏幕。
  3. **第一步 划范围**：先读仓库，别空着手问。配置类读 `.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架配置和 `.github/workflows/*`（其中每个 `secrets.*`/`vars.*` 引用都是向导必须产出的值）；迁移/割接类弄清当前状态、目标状态和中间的不可逆动作。然后把有序的阶段列表和每个阶段产出的值给用户看并确认（可增、可删、可重排）。**完成标准**：每个阶段都有名字且有序；每个捕获的值都知道 (a) 人类从哪里拿到、(b) 写到哪里（`.env`、GitHub secret、两者、或哪里都不写，有些阶段是纯动作）、(c) 是 secret（隐藏输入）还是公开。
  4. **第二步 绘制每阶段的旅程**：为每个阶段写出人遵循的精确路径：打开哪个 URL、在那里做什么、值显示在哪、填哪个变量，例如 "Dashboard → Developers → API keys → Reveal test key → copy"。不知道当前 UI 或确切命令时就明说并问用户或查文档，**绝不编造可能不存在的步骤**。
  5. **第三步 撰写**：把 `template.sh` 复制到目标路径，按依赖顺序每个步骤一个 `stage` 替换示例阶段，设好 `TOTAL_STAGES`。使用库辅助函数：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。守住模板设的线：先打开 URL 再要它的值；secret 一律 `ask_secret`；每个要持久化的值都 `write_env`；`set_secret` 只写 CI 真正需要的；任何不可逆动作前 `confirm`。
  6. **第四步 校验与交接**：`bash -n <script>`，有 `shellcheck` 就跑；`chmod +x <script>`；**不要自己端到端运行**（它会开浏览器并阻塞等待人工输入），改为静态追踪：第一步的每个值都被捕获并落到第一步说的位置，每个 `set_secret` 的名字都精确匹配 CI 里的一个 `secrets.*` 引用。最后告诉用户怎么运行。
  7. **为什么在 engineering 而非 productivity**：它会读 `.env*`、`docker-compose*`、框架配置和 `.github/workflows/` 里每个 `secrets.*`/`vars.*` 引用来给自己划范围，会写 CI secrets，并用 `bash -n` 和 `shellcheck` 校验产出。description 就是决定它何时触发的指针：它产出什么、四个触发分支（配置基础设施、设置凭证或 CI secrets、走一遍不熟悉的第三方仪表盘、一次性迁移或割接），以及一个明确的**非触发**：agent 自己能做的步骤不要用它，agent 能做的活就该 agent 干。

## 二、productivity（生产力类，7 个）

### `grill-me`

- **一句话定位**：对用户进行一场严苛的面试式提问，以打磨某个计划或设计方案
- **调用方式**：用户手动调用
- **适用场景**：用户希望用"grill"相关触发词启动一个面试式的深度问答流程。与 `grill-with-docs` 的分流依据是用户当前**是否在一个工作目录里**
- **核心指令**：此 skill 本身只是一个入口壳，全部内容是调用 Skill tool 并传入 `grilling`。调用后将启动 grilling skill 的完整流程。
- **实现要点**：源码用显式的 `Call the Skill tool with "grilling"` 而非散文式的 "run the `/grilling` skill"。后者并不能可靠地让技能加载，这正是 `grill-with-docs` 被报告最多的问题背后的已知粗糙边缘；去掉开头的 `/` 同时让指令不再假设 Claude Code 的触发语法，从而与 harness 无关。

### `grilling`

- **一句话定位**：针对某个计划、决策或想法，对用户进行持续不断的深度追问，按"设计树 + 前沿 + 轮次"组织
- **调用方式**：模型自动调用
- **适用场景**：用户想要压力测试自己的思考；使用任何"grill"相关触发短语时。措辞已泛化（"this plan" → "this"，"enact the plan" → "act on it"），可作为对任何计划、决策或想法的压力测试，不再局限于软件计划
- **核心指令**：
  1. **把访谈映射为设计树**：每个决策分支到挂在它下面的决策。
  2. **按轮次推进**：**前沿（frontier）** 是前置条件已定的全部决策，即不必猜测未听到的答案现在就能问的问题。**一轮问完整个前沿**：每个问题编号并给出推荐答案，然后等用户答完再进下一轮。同样 13 个问题约 3 轮问完，而不是 13 轮。
  3. **轮格式固定**：`❓ **Q1** - **<问题标题>**: <正文，可含多段与多选>`，空行，`➡️ <推荐答案>`，空行，`---` 分隔，再下一个问题。推荐答案单独占一行 `➡️`，与问题视觉分离，使用户能按编号回答而不必把问题引回去；连续问题之间用水平分隔线，不要连在一起。
  4. **把问题措辞改造成"是"即接受推荐**：让用户能用一个"是"来认可你的推荐答案。
  5. **重算前沿**：每轮回答都会重塑决策树，已定的决策把前沿向外推、解锁依赖它的问题。答案依赖本轮仍未关闭的问题的那个问题属于**更晚的一轮**，不属于这一轮。
  6. **找事实是你的活，不是用户的**：前沿问题需要环境中的事实（文件系统、工具等）时，派 sub-agent 去查，不要问用户你自己能查到的东西。但**不要阻塞**：正在进行的探索是一个未定的前置条件，只有依赖它的问题等 sub-agent 汇报，前沿其余问题现在就问。**决策权属于用户**：每个决策都要摆给用户并等待。
  7. **收尾条件**：前沿为空时会话结束，设计树每个分支都走过，没有任何东西被默默假定。在用户确认达成共识之前不要行动。

### `handoff`

- **一句话定位**：将当前对话压缩为交接文档，方便另一个 agent 接手继续工作
- **调用方式**：用户手动调用（可带参数：下一次会话用来做什么）
- **适用场景**：**只在上下文需要搬运时**：换 harness、换目录、交给同事、或在某个 phase 中途 fork 出的支线任务。它买的是可移植性，不是上下文窗口之间的通用桥梁。同 harness 同目录的 phase 边界处应该用 `/compact` 而不是它
- **核心指令**：
  1. 撰写一份交接文档，总结当前对话内容，使全新的 agent 能无缝继续工作。
  2. **保存到用户操作系统的临时目录**，不是当前工作区。解析顺序固定：`$TMPDIR`，否则 `/tmp`；Windows 上为 `%TEMP%`。每次运行用同一套顺序解析并报告路径。
  3. 包含"建议使用的 skills"（suggested skills）一节，写明下一个 agent **应该用 Skill tool 调用**哪些技能。
  4. 不要重复其他制品（spec、计划、ADR、issue、commit、diff）中已有的内容，改用路径或 URL 引用。
  5. 脱敏处理：隐去 API 密钥、密码、个人身份信息等敏感内容。
  6. 如果用户传入了参数，将其视为下一次会话的重点方向，据此调整文档内容。

### `teach`

- **一句话定位**：在当前工作区内教用户一项新技能或概念，支持跨会话的持续学习
- **调用方式**：用户手动调用（可带参数：想学什么）
- **适用场景**：用户想要系统性地学习某个主题；希望获得结构化的课程、练习和参考资料。这是一个**有状态**的请求，用户打算跨多个会话学习该主题
- **核心指令**：
  1. **教学工作区**：把当前目录当作教学工作区。**路径锚定**：`./lessons/` 等工作区路径从 `/teach` 被运行的目录解析，只有 `*-FORMAT.md` 链接从该 skill 自己的文件夹解析。学习状态由以下几处承载：
     - `MISSION.md`：用户为什么对这个主题感兴趣，用于给所有教学打底（格式见 `MISSION-FORMAT.md`）
     - `./reference/*.html`：参考材料目录，是课程的压缩精华、学习的原始单元，应是打印效果好、便于速查的漂亮文档
     - `RESOURCES.md`：可探索以获取知识与智慧的资源清单（格式见 `RESOURCES-FORMAT.md`）
     - `./learning-records/*.md`：学习记录，类似软件里的 ADR，记录非显然的教训与关键洞察，命名 `0001-<dash-case-name>.md` 编号递增；用于计算最近发展区（格式见 `LEARNING-RECORD-FORMAT.md`）
     - `./lessons/*.html`：课程目录，命名 `0001-<dash-case-name>.html` 编号递增
     - `./assets/*`：跨课程复用的**组件**
     - `NOTES.md`：记录用户偏好或工作笔记的草稿本
  2. **教学哲学**：深度学习需要三要素：**知识**（来自高质量高可信资源）、**技能**（通过你设计的高相关度互动课程习得）、**智慧**（来自与其他学习者和实践者的互动）。在 `RESOURCES.md` 充实之前，重点应是找高质量资源，**永远不要相信你的参数化知识**。
  3. **Fluency vs Storage Strength**：区分即时提取的**流利度**与长期保持的**存储强度**。流利度会给用户掌握了的错觉，存储强度才是真目标。课程要用"必要的难度"构建长期记忆：**检索练习**（凭记忆回忆）、**间隔重复**（把练习分散到时间上）、**交错练习**（混练不同但相关的主题，仅用于技能练习）。
  4. **课程设计**：课程是主要产出。每节课是一个自包含 HTML 文件，只教一件范围很窄、与 mission 挂钩的事；应美观（Tufte 风格、清晰易读的排版）、简短、能很快完成（学习者工作记忆很小），并给用户一个可累积的实在收获，且落在用户的最近发展区内。尽量用 CLI 命令帮用户打开课程文件。每节课用 HTML 锚点链接到其他课程和参考文档，推荐一份最优质的一手资料供阅读观看，并提醒用户向 agent 追问（agent 就是老师）。
  5. **组件复用**：`./assets/` 存样式表、小测组件、模拟器、图示助手等。**复用是默认而非例外**：写课前先读 `./assets/`，从已有组件搭；需要新的可复用物时写成组件并链接，**绝不内联**未来课程会重复的代码。共享样式表是每个工作区赢得的第一个组件。
  6. **Mission 驱动**：每节课都要与 mission 挂钩。mission 不清或 `MISSION.md` 未填充时，第一件事是追问用户为什么想学。mission 可能随用户成长而变化，这很正常。更新 `MISSION.md` 并加一条学习记录，**改 mission 前先与用户确认**。
  7. **最近发展区**：用户始终应感到"刚好被挑战"。用户没说具体学什么时，通过读 `learning-records`、结合 mission 判断该教什么来推断，教最相关且落在 ZPD 内的东西。
  8. **知识与技能的分工**：知识部分要降低认知负荷（难度是知识的敌人，它吃掉理解所需的工作记忆），引用外部资源并**密布引用出处**；技能部分要增加"必要的难度"（难度是技能的工具，费力的检索才构建存储强度），通过互动课程、引导用户完成真实步骤清单来教，每种都建立在**反馈环**上，且反馈要尽可能紧、最好自动即时。
  9. **小测出题规则**：小测每个答案的**词数（尽可能字符数也）完全相同**；**正确答案的位置逐题变化**；不要通过格式或顺序给用户任何线索。
  10. **智慧获取**：用户的问题看似需要智慧时，默认姿态是先尝试回答，但最终委托给**社区**（论坛、subreddit、线下课程、本地兴趣小组）。应主动找高声誉社区推荐；用户表示不想加入社区时尊重其意愿。
  11. **参考文档**：建课时同时建参考文档（语法与代码片段、算法与流程图、瑜伽体式、健身动作、术语表）。课程很少被回看，参考文档会。它们应是课程的压缩精华，为速查而设计。**术语表尤其关键**：一旦创建，之后每节课都要遵守它。
  12. **`NOTES.md`**：用户表达教学偏好或需要记住的事时记在这里，便于后续设计课时回看。

### `to-questionnaire`

- **一句话定位**：将用户无法独立回答的决策转化为一份结构化问卷，发给唯一知情者填写
- **调用方式**：用户手动调用（**v1.2.0 起从 in-progress 升入 productivity**）
- **适用场景**：用户需要向他人（同事、客户、领域专家）异步收集信息以推进决策时，或约个会一起填。接收者持有用户缺乏的知识，问卷把它从接收者那里取出来。在 `ask-matt` 中被定位为 `/grill-me` 的**反向操作**（grill 的是别人而不是自己）
- **核心指令**：**访谈"发送"而非"主题"**：普通 grilling 会拷问主题，而这里主题恰恰是用户答不了的，所以只问用户关于**发送**的事（这他们总能回答）：问卷发给谁、需要拿回什么。文档里的问题则瞄准接收者所知与用户所需之间的**差距**。
  1. **发给谁？** 用一轮交流问清接收者的角色、专长和与用户的关系。这决定问卷的语气和需要携带多少上下文。完成标准：知道接收者是谁、以及他们知道什么用户不知道的东西。
  2. **需要拿回什么？** 用一轮交流问清用户无法独自解决、需要从这个人那里得到的具体决策或事实。完成标准：拿到一份具体清单，写清用户最终必须能做什么或决定什么。
  3. **写问卷**：按下面的文档结构，针对第 1–2 步得出的差距起草问题。写入当前目录的 `to-questionnaire-<slug>.md`（slug 取自主题）并报告路径。完成标准：文件存在，且用户在第 2 步点名的每一项都被某个问题覆盖。
- **文档结构**：把文档框定为一份**发现式问卷**（用户缺上下文，接收者有）。问题按**最重要在前**排序，因为异步意味着你可能只拿到一轮。问题超过一把就按主题归到 `##` 标题下。模板：`# <标题>` → **Purpose:**（问卷为何存在、押在上面的决策）→ **From:** / **To:** / **How your answers will be used:** → `## Context`（一段话给不在用户脑子里的接收者定向，够答好就行）→ `## How to answer`（截止时间与大致工作量；部分回答和"我不知道"都有用，不确定就标注而非跳过）→ 每个主题一个 `## <主题标题>`，段内问题最重要在前，每个问题只有一个点子、绝不复合，问题正下方直接跟一个答案占位（`>`），只在问题可能被误读或招来敷衍答案时补一行 _Why this matters_ → `## Anything else?` 收尾兜底。

### `wait-what`

- **一句话定位**：模型话太多/没讲懂时的单字纠正："等等，重讲一遍"
- **调用方式**：用户手动调用（**v1.2.0 新增**）
- **适用场景**：某条消息**没有落地**的那一刻就敲它，agent 会重新讲一遍
- **核心指令**：全文只有一句："等等，我不明白你讲到哪里了。重讲一遍：给我一点上下文，用 ASD-STE100 简化技术英语讲，并使用 `GLOSSARY.md` 里的统一语言（仓库有多个上下文时，跟随 `GLOSSARY-MAP.md` 找到对应的那个）。"
- **设计意图**（理解它为什么只有三行）：
  - **机制就是名字本身**。讲求简洁的技能失败的方式是膨胀：400 行的技能依然会让模型啰嗦。所以这个技能是一个精确的领头词，别无他物。
  - **描述输出的名字会反效果**。`/tldr`、`/no-fluff` 这类名字让模型砍词，反而让你更听不懂；命名**听者的状态**则同时要到两半：更少的词，和你缺失的上下文。
  - 它复用了你全局 `CLAUDE.md` 里已有的领头词，让技能、`CLAUDE.md` 和每份 `GLOSSARY.md` 伸手够向同一批 token。
- **边界**：它只修一条消息，不预防下一条。术语混乱的根本解药是事先用 `/grill-with-docs` 建立共享语言；`wait-what` 是你还没有那种语言时伸手够的东西。

### `writing-for-agents`

- **一句话定位**：写给 agent 看的文档的写作参考手册：用一套可预测性杠杆让 agent 每次都走同一个**过程**
- **调用方式**：模型自动调用（**v1.2.0 由 `writing-great-skills` 更名并重构**，旧名直接消失、无别名）
- **适用场景**：创建或编辑 skill，或修改 `AGENTS.md` / `CLAUDE.md` 时。参考范围已从"只讲 skill"扩展到**agent 会消费的任何文档**：skill、`AGENTS.md`/`CLAUDE.md`、被指针引到的文档。包装不同，写作相同：同一套杠杆让每一样都可预测，因为 agent 每次运行走相同的**过程**，而不是产出相同的输出
- **配套文件**：写的是 skill 时，另读 `SKILL-MECHANICS.md`（frontmatter、调用方式选择、router 技能）
- **核心指令**：
  1. **上下文指针（context pointer）**：agent 上下文中持有的一份引用，指名某份不在上下文中的材料，并编码触达它的条件。skill 的 description 是一个，`AGENTS.md` 里指名某文档的一行是同一个对象。**指针的措辞**（而不是它的目标）决定 agent 何时触达材料、以及多可靠。一个"必须有"的目标配一个弱措辞的指针是一个**方差 bug**：先磨措辞，磨不动了才把材料内联。指针做两件事：说明材料是什么，列出应触达它的**分支**（分支是文档处理的一个 distinct 情形，不同运行走不同路径）。常驻指针的每个词每轮都要付费，所以它比正文更该被修剪：**前置领头词**、**一个分支一个触发词**（给同一分支改名的同义词是一个分支写了两遍，合并）、**砍掉正文已承载的身份信息**。
  2. **两种负荷**：每加一份文档或指针都花掉两种预算之一。**上下文负荷**是常驻材料对 agent 窗口的开销（`AGENTS.md` 一行、skill description，每轮都在上下文里，不管是否触发都在花 token 和注意力）。**认知负荷**是对人的开销（有哪些文档、各自何时伸手）。**人是索引**。它不是要最小化的成本，而是人类主体性的代价：在人的判断重要处花它，在不重要处移除它。只经指针触达的材料以指针自身那一行为代价逃过上下文负荷；完全没有指针的材料完全骑在认知负荷上。
  3. **信息层级**：文档由两类内容构成：**步骤**（agent 执行的有序动作）和**参考**（按需查阅的定义、规则、事实），二者可自由混合。核心决策是每块材料放在**信息层级**（按 agent 多迫切需要材料排序的梯子）的哪一级：①**文件内步骤**是首要一级，agent 按序做什么；②**文件内参考**按需查阅，常常是一个合理平级的同侪集合（一份审查的全部规则在同一级），这是好安排不是坏味道；③**披露参考**被推到单独文件，由上下文指针触达，只在指针触发时加载，范围从同文件夹的兄弟文件一直到完全外部、任何文档都能指向的参考。往下推太少顶层会膨胀，推太多会把 agent 实际需要的材料藏起来，这个张力就是全部决策。
  4. **渐进披露（progressive disclosure）**：沿梯子往下走（移出主文件、藏到指针后面）让顶层保持可读的动作。它 primarily 不是 token 优化，而是层级受保护的方式。**分支**是最干净的披露测试：内联每个分支都需要的东西，把只有部分分支会触达的东西推到指针后面。文档有步骤时，**本该披露的文件内参考会把步骤埋起来**，让注意它们变成抛硬币。这是方差杠杆，不只是可读性杠杆。
  5. **共置（co-location）**：梯子的文件内伙伴：梯子决定一块材料**往下走多远**，共置决定它到了那级之后**旁边放什么**。把一个概念的定义、规则、注意事项放在同一个标题下而不是散落各处，这样读一部分能把它的邻居一起带来。测试：文档读起来应像是**为 agent 写的文档**。（与重复不同：重复是在两处说同一个意思；散落是把一个意思碎成多片。）
  6. **Sprawl（膨胀）**：这里的失败模式是文档单纯太长，即便每行都是活的和唯一的。注意力在过量中变薄，多出的每一行都是又一行要维护相关性的。解药是梯子：把参考披露到指针后面，按分支或序列切分，让每条路径只带它需要的。
  7. **步骤与完成标准**：每个步骤都收在一个**完成标准**上（告诉 agent 工作做完的条件）。两个属性让它成为杠杆：
     - **清晰度**：agent 能否区分做完与没做完？模糊的边界（"达成理解"）会招来**过早完成**：在工作真正完成前就结束步骤，注意力滑向"处于完成状态"。前面仍可见的步骤（**完成后步骤**）提供拉力，标准的清晰度是阻力。按序防御：**先磨边界**（局部且便宜）；只有当它本质模糊**且**你观察到抢跑时，才通过切分序列把后续步骤藏起来。隐藏只在跨越真实上下文边界时有效（交接或 subagent 派发；内联调用会把后续步骤留在上下文里，什么都清不掉）。
     - **要求度**：它要求多少。"每个改动的模型都被交代"比"产出一份变更清单"更能迫使做透。要求度驱动**跑腿活**（agent 在工作内部做的挖掘，潜伏在措辞里而不是写成独立步骤），且它不受步骤约束："每条规则都应用"约束一份平铺参考，正如"每步都做完"约束一个序列。这就是一份纯参考文档如何仍然扛着一条穷尽性标准。
     最强的完成标准同时**可检验**且**穷尽**。
  8. **何时切分**：切一份文档为两份要花掉两种负荷之一，所以只在切口划得来时才切。**按序列**：切在一段步骤上，当完成后步骤诱惑 agent 草率对待眼前这一步时；警惕反面：合并序列会把每一步的后续步骤暴露给跟着它的东西，招来过早完成。**按调用方式**：skill 专属，见 `SKILL-MECHANICS.md`。
  9. **领头词（leading word）**：一个已活在模型预训练里的紧凑概念，agent 运行文档时用它思考（_lesson_、_fog of war_、_tracer bullets_）。作为 token 重复而不是作为句子重复，它会积累一个分布式定义，并用最少的 token 锚定整片行为区域：招募模型已持有的先验。自造词只要你定义清楚也能用，但**编造的词招募不到先验**：你付的是定义 token，而预训练给的词免费；先伸手够已有的词。它锚定两次：在正文里是**执行**（词每次出现，agent 都伸手够同一行为；在平铺参考里它把注意力聚焦到一类要找的东西上），在指针里是**调用**（当同一个词活在你的提示词、你的文档和你的代码库里，agent 会把那份共享语言与材料关联起来，更可靠地触达它）。猎求用领头词重构的机会：三处拼写出来的三元组、花一句话 gesture 一个想法的指针，每一处都是哀求塌缩成单个 token 的段落：`"fast, deterministic, low-overhead"` → _tight_（一个 _tight_ 循环）；`"a loop you believe in"` → _red_，把模糊的门变成二元的可观测状态。你赢两次：更少 token，以及一个更锋利的钩子让 agent 挂住思考。**假定每份文档都扛着领头词能退休的复述，去找出来。**
  10. **否定（negation）**：紧邻这个杠杆的失败模式：用禁止来转向会把被禁的行为拖进上下文，让它**更**可用而非更少。别想大象，大象就成了全部；否定是个弱修饰语，被强激活的概念冲垮，于是禁令有一半被读成"去做那件事"的指令。**提示正向的**：陈述目标行为（"写单行注释"），让被禁的那个根本不被说出口。一条禁止只在它是你无法正向表述的硬护栏时才配占位；即便如此，也要配上正向目标。
  11. **修剪**：①每个意思保持**单一事实来源**，一个权威位置，改行为是一处编辑；**重复**（同一意思在多处）花维护和 token，并把一个意思在梯子上的显著性抬到超过它的真实等级。②**环境也是事实来源**（`package.json` 脚本、配置文件、目录布局、`--help` 输出），复述它的文档是一份**缓存**：一次查找的副本，只在查找很贵时才配得上它的加载；缓存 agent 靠看找不到的东西（不成文的约定、一个选择背后的理由、没有配置会承认的坑），把"一文件一命令"的查找留给环境，那里它们不会过期。③逐行检查**相关性**：更短的文档更容易保持相关；没有修剪纪律，默认结局是**沉积**：层层陈旧沉积下来，因为添加感觉安全、移除感觉冒险。④逐句猎**空操作（no-op）**：一条模型默认就会遵守的指令付了加载费却什么都没说；测试（相对默认它是否改变行为？）是**模型相对**的而非读者相对的，两个人有分歧就靠运行文档来解决，不靠辩论；句子不达标时**删掉整个句子**，而不是从里面修剪字词。这个测试同样给领头词分级：一个弱到打不赢默认的词（agent 已经够 thorough 时的 _be thorough_）是空操作，解药是更强的词（_relentless_）。
- **配套分支 `SKILL-MECHANICS.md`**（v1.2.0 新增，承载 skill 专属机制）：
  - **调用方式二选一**，交换的是那两种负荷。**模型自动调用**的技能保留 `description`，agent 能自主触发它，其他技能也能触达它；你照样能敲它的名字（模型调用总是**包含**用户触达，description 只会增加 agent 发现，从不拿走人的）。description 是技能的顶层上下文指针，被迫常驻：以永久上下文负荷换可发现性。内容全是参考的模型自动技能也是共享参考的一个归宿：另一个技能能调用它，所以多个技能都需要的参考住在一处。机制：省略 `disable-model-invocation`，写一段面向模型、携带触发分支的 description。**用户手动调用**的技能把 description 从 agent 的触达中剥掉：只有人敲名字能调用，没有其他技能能。零上下文负荷，但花认知负荷：**你是那个必须记住它存在的索引**。机制：设 `disable-model-invocation: true`，`description` 变成面向人的一行摘要，触发清单被剥掉。
  - **选择规则**：只在 agent 必须自己伸手够到它、或另一个技能必须够到它时才选模型调用。如果它只靠手触发，就做成用户手动调用，不付上下文负荷。
  - **共享参考的归属**：两个用户手动技能都需要的共享参考无处可放（没有 description，谁也触发不了谁）。把它推到技能系统之外的普通文件：任何技能都能指向的外部参考。
  - **按调用方式切分**：当你有一个 **distinct 领头词**应该独立触发它时（一个你真的会在提示词里用的触发词），或另一个技能必须够到它时，切出一个模型自动技能。你为新的常驻 description 付上下文负荷，所以那份独立触达必须划得来。
  - **Router 技能**：当用户手动技能多到你记不住，堆积的认知负荷由一个 **router 技能**治好：一个用户手动技能，指名其他技能以及各自何时伸手，让人只需记一个技能。它**只能提示，绝不能触发**：用户手动技能没有 description，除了人没有东西能触达它们。

### `git-guardrails-claude-code`

- **调用方式**：模型自动调用
- **适用场景**：用户希望防止破坏性 git 操作、添加 git 安全钩子、阻止 Claude 执行 `git push`/`git reset --hard` 等命令时触发。

### `setup-pre-commit`

- **一句话定位**：在当前仓库中配置 Husky pre-commit hook，集成 lint-staged（Prettier）、类型检查和测试。
- **调用方式**：模型自动调用
- **适用场景**：用户希望添加 pre-commit 钩子、配置 Husky、设置 lint-staged、或为提交增加格式化/类型检查/测试门禁时触发。
- **核心指令**：
  1. 检测包管理器：根据 lock 文件判断（npm/pnpm/yarn/bun），默认 npm。
  2. 安装 devDependencies：`husky`、`lint-staged`、`prettier`。
  3. 运行 `npx husky init` 初始化，创建 `.husky/` 目录并在 package.json 添加 `prepare` 脚本。
  4. 创建 `.husky/pre-commit`，依次执行 `npx lint-staged`、typecheck、test（后两者若 package.json 无对应脚本则省略并告知用户）。
  5. 创建 `.lintstagedrc`，对所有文件运行 `prettier --ignore-unknown --write`。
  6. 若无 Prettier 配置则创建 `.prettierrc` 默认配置。
  7. 验证各文件就位后，提交所有变更，提交本身会触发 pre-commit hook：这是一次很好的冒烟测试，证明整条链路能工作。

### `chief-of-staff`

- **一句话定位**：扮演 chief of staff，在**单个会话**中协调 subagent 与日程去追求一个长期目标，同时做战术执行与长期战略决策。
- **调用方式**：用户手动调用
- **适用场景**：有一个需要长期持续推进的目标（而非一次性任务），希望由一个"直接负责人"持续运营，会话会运行很久，逐步积累部落知识（tribal knowledge），并辅助用户做长期战略决策。
- **核心指令**：
  1. **双重身份与双轨思考**：你是这个目标的 Directly Responsible Individual（DRI），被授权比平时思考得长远得多，必须同时跑两条轨道，**战术**：怎么完成眼前这个任务？**战略**：怎么改造环境，让*下一个*任务的结果更好？
  2. **全部工作放进 subagent**：所有实际工作都应由 subagent 完成，以保护你自己的上下文窗口；使用**后台 agent**，这样你才能与用户保持持续对话。
  3. **稀疏通信 + context pointer**：与 subagent 的往来通信要稀疏，主要靠**上下文指针**传递：研究笔记、此前的 commit 等，指针已能提供的信息不要重复传递。
  4. **日程（Schedules）**：在 harness 允许的前提下，主动建议能推进该目标的**周期性日程**。
  5. **战略视角优先**：作为任何一切工作的**第一步**，先考虑 agent 所处的环境能否被改善。agent 在**成功之坑（pit of success）**里才茁壮：极度受限的 API 与函数、强制正确性的 lint 规则、能让代码评审执行最佳实践的 `CODING_STANDARDS.md`。它们还需要相关的**数据源**才能成事：关键运行进程（如 dev server，或生产环境）的日志、测试环境数据库的访问权、必要时的浏览器访问权（点击浏览、截图）。
  6. **"no workarounds" 规则**：打造遵守该规则的环境（与代码库）：不允许一次性变通方案或绕过既定流程的 hack；任何对约定的偏离都必须在功能开发之前被主动修掉。
  7. **Relentless 改进环境**：把每一条用户消息都当作一次寻找上述改进机会的借口。

### `claude-handoff`

- **一句话定位**：将当前对话写成交接摘要，通过 `claude --bg` 启动一个后台 agent 立即接手继续工作。
- **调用方式**：用户手动调用
- **适用场景**：需要把当前会话上下文转交给一个全新的后台 agent 继续推进时（如长时间运行的工作移交后台执行）。
- **核心指令**：先写一份 handoff summary 存到**用户操作系统的临时目录**，再用 `claude --bg --name "<描述性名称>" -- "$(cat <summary file>)"` 以该文件内容为 prompt 启动后台 agent。**经文件传递而非 shell 内联展开**，可避免摘要中的反引号被执行、`$` 被展开。agent 在当前工作目录启动并立即返回，用户用 `claude agents` 管理。必须传 `-n`/`--name` 设置可读名称（如 `--name "Fix login bug"`），它决定任务列表、会话选择器和终端标题中的显示名。摘要中要包含 "suggested skills" 一节，指明下一个 agent 应对哪些技能调用 Skill 工具。不要复制其他制品（specs、plans、ADRs、issues、commits、diffs）已承载的内容，改用路径或 URL 引用。必须脱敏 API key、密码、PII 等敏感信息。摘要就是 agent 的 prompt。若用户传了参数，把它当作下一会话的聚焦方向，据此裁剪摘要。

### `loop-me`

- **一句话定位**：通过有状态的 grilling 会话，把用户生活/工作中重复出现的模式访谈成可实施的工作流规格。
- **调用方式**：用户手动调用
- **适用场景**：想识别并设计生活中可委派的重复模式（loop），将其固化为 `workflows/*.md` 中的工作流规格；也可不带参数让 agent 自己去发现值得规范的 loop。
- **核心指令**：运行一个有状态的 `/grilling` 会话，唯一产出是 **workflow** 规格；采用 grilling 纪律（穷追不舍、**每轮一次提出一组问题**、每个问题附推荐答案），随访谈结论创建、编辑、删除规格。核心视角：**loop** 是生活中反复出现的模式（职业、一周、一个早晨、某项重复活动），把生活看成环环相扣的 loop 才能看出哪些活动足够可预测、因而值得**委派**；**workflow** 是某个 loop 的规格，你是在 loop 上运行 workflow。共享词汇只在工作流需要时使用，绝不是清单，且**不强制任何结构**：除非 grilling 证明有必要，工作流不需要 AI、不需要 checkpoint、不需要 schedule。词汇：**Trigger**（触发方式，event 如新邮件/新 issue，或 schedule 如每天早晨，事件触发通常更高效）、**Checkpoint**（人工介入点，有些工作流完全没有、全自动运行，有些根本不用 AI）、**Push right**（把 checkpoint 尽量往后推，先做最大量的工作，让人类只被问一次、很晚才被问且一切已备好）、**Brief**（checkpoint 呈现给用户的东西：紧凑、可决策的摘要：产出了什么、为什么、以及一个指向资产本身的下沉链接，绝不是原始输出；审阅速度是硬要求）。**完成定义**：一份规格只有在实施 agent 能一个问题都不问就把它建出来时才算完成，只要还有问题没解决就没完成。工作区：`workflows/*.md` 每份规格一个文件；`NOTES.md` 记录用户世界的原始笔记：他们用的工具、他们处理的渠道、以及他们对两者的自有术语，为空或太薄时先访谈再规范，出现模糊术语就当场打磨成规范词并记录在此。

### `setup-ts-deep-modules`

- **一句话定位**：为 TypeScript 仓库接入 dependency-cruiser，把每个包封装成"深模块"：实现藏在子目录里，外部只能经由入口文件访问。
- **调用方式**：用户手动调用
- **适用场景**：TypeScript monorepo 需要确立包边界规则，防止跨包深层私有导入、遏制 barrel 文件滥用、让代码对 AI agent 可导航时。
- **核心指令**：
  1. **目标形态**：每个包都是 **deep module**（小接口后藏大量行为），公开面是包的**入口点**（包根目录下的文件），子目录里的一切对外隐藏。规范布局：`src/packages/<name>/` 下 `index.ts`、`client.ts` 等为入口点，`lib/` 放实现，`tests/` 放共置测试与夹具。包是**扁平**的：根下只有一层子目录，包内实现可任意深嵌套，但包中不能再有包。
  2. **四条 error 级规则**：①**入口点边界**：包外代码（app 或其他包）只能导入该包的入口点（根文件），绝不能碰其子目录；②**包内自由**（包内文件彼此自由互引）；③**测试走入口点**：`<pkg>/tests/` 下文件可导入任意包的入口点和本包 `tests/` 夹具，但不能导入任何包的子目录内部（连自己的也不行），跨包集成测试允许、深层导入不允许；④**无循环依赖**。配置文件另含 `tests-folder-is-private` 规则，保证 `tests/` 目录只能被测试访问。
  3. **入口点而非 barrel**：因为公开面是**每一个根文件**，包可以暴露多个小入口点（`index.ts`、`client.ts`、`server.ts`），而不必把所有东西挤进一个巨型 `index.ts`；明确不鼓励 re-export 整棵子树的 barrel 文件。分层（哪些包可依赖哪些包）是另一回事，在配置里以注释桩留给本仓库自行填写。
  4. **七步流程**：①**检测环境**：据 lock 文件判定包管理器（`pnpm-lock.yaml`→pnpm、`yarn.lock`→yarn、`bun.lockb`→bun，否则 npm）；有 `src/` 则包根为 `src/packages`，否则 `packages`；已有 `.dependency-cruiser.*` 配置时**绝不覆盖**，改为合并规则并告知用户加了什么。②安装 `dependency-cruiser` 为 devDependency。③把自带 `dependency-cruiser.config.cjs` 拷到仓库根并设好 `PACKAGES_ROOT`。④接入检查：新增 `lint:boundaries` 脚本（`depcruise <packages-root>` 或 `depcruise src`），并折进仓库已有的、跑 typecheck 的那个总检查命令（`check`/`ci`/`validate`）；不要动 `tsconfig`、不要加路径别名。⑤搭建 `<packages-root>/example/` 可复制模板：`index.ts` 导出函数并委托给内部文件（visibly deep），`lib/impl.ts` 藏实现，`tests/example.test.ts` 只导入 `../index`。⑥**证明规则会咬人**（整个技能的完成标准）：先跑通 clean example，再临时往测试里加深层导入 `import { thing } from "../lib/impl"`，必须报 `tests-through-entrypoints` 失败，还原后再跑必须通过；若第 2 步不失败说明规则没接对，修好再结束。⑦在**包目录内**写 `<packages-root>/README.md`（布局说明、"只通过入口点导入"、如何跑 `lint:boundaries`，明确劝阻 barrel），再从仓库的 agent 指令文件（`CLAUDE.md`，没有则 `AGENTS.md`，都没有就建 `AGENTS.md`）加一行 context pointer 指向它，让 agent 能发现边界规则而不是撞上去。
  5. **易错点**：公开/私有由**深度**决定：根文件是入口点，任何子目录都是私有，所以新增文件夹永远不需要改配置；配置用 `.cjs` 而非 `.js`，以保证 `"type": "module"` 仓库里 `module.exports` 仍可用；配置里的 `$1` 回引（dependency-cruiser 的 group matching）正是"包能访问自己内部、外人不能"的关键，不要把它们摊平成一个个按包写的规则。词汇表（deep module、interface、seam、depth）通过调用 Skill 工具加载 `codebase-design` 并全程使用其语言。

### `writing-beats`

- **一句话定位**：把一堆原始素材组装成"beat 之旅"：逐拍推进文章，每个概念必须先"接地"才能被后续的拍使用。
- **调用方式**：用户手动调用
- **适用场景**：写作的**利用阶段**（exploit）：探索已结束、素材堆已固定，需要以 choose-your-own-adventure 的方式确定一条穿越素材的叙事路径。
- **核心指令**：用户传入（或稍后传入）一份 markdown 原始素材，确认一次文章保存路径并记住它。**beat** 是旅程中的一个动作：设场景、落论点、提问题、插一句闲话、转折视角，只做一件事然后停下，把读者放在下一个拍能 pivot 的位置；大小随需要而定（一句话、一小段、或作为独立小品的多段），若某个"拍"需要五段加三个小标题，那是两拍粘在一起，拆开。**Grounding** 是核心约束：每个**概念**都必须先接地：要么**前置概念**（读者开篇就自带，一开始固定），要么**已引入**（某个拍建立了它，此后对后续所有拍都算接地），否则没接地的概念不可使用；单位是概念而非词语，一拍可能在没有术语的情况下就用上了读者缺乏的想法。每拍身兼两职：**要求**已接地的概念，同时**接地**新概念，要维护一份"目前已接地"清单，每落一拍就更新。流程：①先与用户确定前置概念；②从素材中写 2-3 个候选**起始拍**，每个是进入文章的不同入口，各自只能依赖已接地概念并注明它接地了什么，写入文章文件前先给用户看，用户选一个后**预览这一选择会解锁哪些拍**，像让用户朝路径下方瞥一小段；③只把用户选中的那一拍写入文章文件，写完停下；④从磁盘重读文章文件，再提供 2-3 个候选**下一拍**，方向各不相同，但都必须从当前已接地集合可达，并注明各自接地什么；⑤循环至旅程自然结束。素材是采石场，可改写、拆分、重组、引用，文章在旅程完成时结束而非素材用完时，剩下没用上的片段是正常的。写作节奏：一次只追加一拍、绝不提前写；每次写入前从磁盘重读文件，绝对保留用户编辑；用户大幅改了前一拍就让它影响后续；用户说"重写那一拍"或"回去换第 3 拍"就地改、其余不动。

### `writing-fragments`

- **一句话定位**：写作的**探索阶段**：通过穷追不舍的访谈从用户身上挖掘原始片段（fragment），此阶段不施加任何结构。
- **调用方式**：用户手动调用
- **适用场景**：写作初期有大量想法但尚未定型，需要自由探索、积累素材片段，为后续 exploit 阶段（`writing-beats`/`writing-shape`）准备原料堆。
- **核心指令**：这是纯 **explore**：扩大"可能写出什么"的空间而不对结构作出承诺，承诺属于 *exploit*，是另一个技能的职责。运行一个产出片段的 grilling 会话，就用户想写的任何话题 relentlessly 访谈；在此施加阶段划分、大纲或文章结构都属于越界。随着片段从对话双方浮现，把它们追加进单个 markdown 文件；用户没给路径就问一次并在此后记住。从用户开口的第一句话（含初始 prompt）就开始捕获片段。首次写入时在顶部放唯一一个 H1 工作标题（之后可改），除此之外什么都不放：无元数据、无目录、无日期。**片段**是任何可能存活进最终文章的文本，只需**作者自己能读懂**（作者知道它是什么意思），不必定义术语、也不必让冷读者看懂，标准是"这是一段好文字吗？"而非"这是一个自洽论证吗？"片段刻意保持异质：一句想在某处投放的锋利句子、带一行论证的判断、小故事（一件事、一段代码、一个场景、一个类比）、半成形的想法（"关于 X 有多像 Y，以后再想"）、一句引文或对话或旁听到的话、凭感觉聚在一起的相关观察清单、一句抱怨/忏悔/punchline，以及最有价值的**主导词（leading word）**：一个能让整篇文章挂在上面的紧凑隐喻或新造词（用一个术语命名整个想法，如同 _tracer bullets_、_fog of war_ 命名一整套模式）。主导词是最值得落下的片段、是承重的：explore 阶段命名对了，它会在之后塑造结构、过渡和标题，在整个 exploit 阶段持续带来回报；当对话围着某个反复出现的想法打转时，要推动为它造一个词。小说家的日记是范本：多年无结构的观察记录，日后被开采成素材，片段就是观察。文件格式：片段之间用水平线（`\n---\n`）分隔，正文内无标题、无标签、除追加顺序外无排序。写作节奏：静默追加，不为每个片段征求许可，顺带提一句加了什么（"adding that"），不要用保存对话框打断对话；每次写入前从磁盘重读文件，用户可能在中途编辑、重排或删除了片段，必须保留其改动，绝不覆盖整份文件，只追加（或应用户要求就地改某个片段）；用户随时可以说"cut the last one"、"rewrite that one sharper"、"merge those two"，这些话都是一等指令。

### `writing-shape`

- **一句话定位**：把一堆原始素材逐段塑造成一篇有论证结构的完整文章，边议定边追加到独立文件。
- **调用方式**：用户手动调用
- **适用场景**：写作的**利用阶段**（exploit）：素材堆已固定，需要以段落为单位构建有论证、有结构的文章。
- **核心指令**：用户传入（或稍后传入）一份 markdown 素材：可以是从整齐的片段清单到一整片无结构文字到一份转录稿的任意形态，格式不重要，先端到端读完整份再动手。把它当作**输入堆**，跑一个 shaping 会话产出一篇**独立的文章文档**；这是 **exploit**：探索已结束、素材堆已固定，对结构作出承诺并开采素材堆来填满它。**绝不编辑素材文件**，它对本技能是只读的。用户没说文章存哪就问一次并记住路径。流程：①通读素材堆，形成对其中内容的判断；②与用户确定读者开篇自带哪些概念（**Grounding** 约束与 beats 相同：每个概念要么前置、要么已被前面的块引入，未接地的概念不能被后续块依赖，单位是概念而非词语，概念有名字时要把想法和术语一起落地），维护一份"目前已接地"清单，当你问"读者接下来需要听到什么"时，下一步所需的某个未接地概念本身就是答案：先在此处或更早的块里接地它，否则走不出这一步；③起草 2-3 个候选开头，每个暗示不同的论点/角度，全部展示，逼用户选一个或组一个混合体，选定的开头决定了文章其余部分必须做什么；④**逐段生长**：开头落定后反复问"基于这个开头，读者接下来需要听到什么？"，从素材堆里取料回答；下一块只能依赖已接地概念并在落地时接地新概念，同时与用户**争论这一块该采取什么形态**：段落、列表、表格、callout、引文、代码块，每个格式选择都要有意识、可辩护；⑤议定一段就立刻追加进文章文件，不批处理，让用户看着文章成形；⑥循环第 ④ 步直到用户认为文章完成。格式权衡要摆到桌面上谈：**prose vs 列表**（prose 承载论证，列表承载并列项，项不是真并列就用 prose）；**inline vs callout**（提示、警告、题外话进 `> [!TIP]`/`> [!NOTE]`，但仅当内联确实会岔开主线时）；**表格 vs 重复结构**（同一形态重复 3 次以上且字段相同才用表格）；**引文 vs 转述**（原文措辞本身就是重点时引用，只在乎想法时转述）；**代码块 vs 行内代码**（多行、可运行或示范性用块，单个 token/标识符用行内）。**对话感**：这是一场反向的 grilling，ideation 时问"你究竟在注意什么？"，这里问"这篇文章究竟在论证什么，读者需要按什么顺序听到它？"，要顶回去，不许弱的过渡滑过去，一段若挣不到位置就删。反复使用的具体动作："这一段为读者做了什么上一段没做的事？""删掉它什么会崩？""这是散文，还是该是列表？为什么是散文？""这个句子在干两份活：拆开或选一个。""开头承诺了 X，我们漂到了 Y：要么把线重新穿回去，要么改开头。"素材堆是采石场不是脚本：取出片段、按周围段落改造、放置到位，可跨段拆分、与他片合并或转述，堆的职责是被开采，文章的职责是读起来像一个声音；堆里缺了文章需要的东西就明确点破差距："这里需要一个例子而堆里没有，现在给我一个，否则砍掉这一段。"写作节奏：每议定一块就追加，每次写入前从磁盘重读文件（用户可能中途编辑过），绝不盲目覆盖；用户要重写某段时就地改那一段，其余不动。**越界事项**：开采堆里没有的新片段（差距按上述方式处理）、编辑素材文件、发布或为特定平台排版、添加用户没要求的 frontmatter。
